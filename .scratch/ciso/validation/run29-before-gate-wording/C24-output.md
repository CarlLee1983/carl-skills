## 2. 判斷

設計明示的流程與信任邊界：

- 供應商 → 公開接收器 → 內部 Redis（第1–2行）：外部輸入進入內部處理。
- Redis → worker／`reconcile` → 正式資料庫（第3行）：訊息取得正式資料處理能力。
- 原始內容 → 儲存桶90日 → 主控台 → 支援人員（第4–5行）：付款資料進入留存及人員存取邊界。

以下皆為**條件式威脅假設**。S／T／R／I／D／E 分別為冒用、竄改、否認、資訊洩漏、阻斷服務、權限提升；未決定的控制不視為不存在。

| 元素及邊界 | STRIDE 假設 |
|---|---|
| 供應商、接收器、外部→內部（1–2、6行） | S：若來源驗證不足，可冒用供應商。T：若無完整性與防重放控制，可修改或重送事件。R：若缺事件紀錄，難以追溯。I：若傳輸保護不足，內容可能外洩。D：若缺大小及速率限制，可耗盡接收或排隊資源。E：若任意事件可觸發特權工作，可提升影響力。 |
| Redis、worker、`reconcile`、資料庫（2–3行） | S：若佇列身分控制不足，可冒用生產者。T：若可修改訊息，可影響對帳。R：若缺跨階段識別碼，難以歸因。I：若讀取權限過廣，可洩漏訊息或資料。D：若缺重試上限及隔離，可造成積壓。E：若事件可選擇越權操作，可濫用正式資料庫能力；具體操作無此證據。 |
| 儲存桶、主控台、支援人員（4–5行） | S：若登入不足，可冒用支援人員。T：若讀寫權限未分離，可更改留存內容。R：若缺存取稽核，難以追查。I：若資料分級及授權不足，可越界讀取付款內容。D：若缺容量配額，可耗盡儲存資源。E：若主控台未將原始內容當資料呈現，可能影響工作階段；呈現方式無此證據。 |

對應緩解與後續驗收證據：

- 接收邊界：來源驗證、完整性、防重放、事件去重、大小及速率限制；以偽造、重送及超量輸入的隔離測試驗收。
- 執行邊界：限定佇列讀寫者、驗證事件結構與業務授權、縮限資料庫權限、設定重試上限；以拒絕未授權訊息及越權操作的程式與測試驗收。
- 留存／人員邊界：資料最小化、唯讀及分域授權、安全呈現、90日刪除、容量限制及稽核；以權限測試、呈現測試、刪除設定與稽核範例驗收。

## 5. 後續

依序請架構負責人確認：

1. 來源驗證、防重放及事件唯一性如何建立？
