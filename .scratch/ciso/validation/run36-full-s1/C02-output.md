### 2. 判斷

已追蹤兩條路徑：

- 登入使用者經 `requireLogin` 提交 `callbackUrl`，連同 session 的 `tenantId` 傳入 `saveHook`（第 2–3 行）。
- `deliver` 先呼叫 `assertSafeUrl`，再以該 URL 發出含 payload 的 POST（第 6–8 行）。

信任邊界是使用者控制的 URL 進入伺服器出站請求。程式已有安全檢查呼叫；其實作缺失，不能假定有效，也不能假定可繞過。

未見角色檢查本身不構成漏洞：無此證據顯示建立 webhook 僅限特定角色。傳入租戶 ID 亦不足以證明完整租戶隔離。

### 3. 發現

**已確認：無。**

**待驗證：callbackUrl 是否可導致 SSRF。**

證據：`src/webhooks.ts:3,7–8`。登入使用者可提供 URL，最終由伺服器發送請求；但能否觸及非預期資源、產生何種結果，無此證據。因此不給嚴重度或完成狀態。

決定性缺口：`assertSafeUrl` 如何處理協定、位址解析、重新導向，以及檢查與實際連線目的地的一致性；出站政策能否限制目的地亦未知。

安全驗證：先讀 helper 與呼叫端，再於隔離環境使用假 payload、受控 DNS／重新導向及模擬內網端點，確認拒絕路徑與實際連線目的地；不得探測部署環境。

交付專案 `/implement` 維護者的**待驗證 brief**：目標是確認上述 SHA 的 URL 信任邊界；補齊 helper、儲存及 delivery 呼叫鏈，證明請求只到允許的目的地。最窄修補尚待證據決定；回歸測試應涵蓋允許與禁止目的地、重新導向及解析變化。
