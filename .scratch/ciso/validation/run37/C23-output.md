### 2. 判斷

資料流與信任邊界：

- 付款商 → 公開 receiver（第1行）：外部請求進入服務。
- receiver → 內部 Redis → worker → 正式資料庫（第2–3行）：外部原始資料進入內部處理及高權限作業。
- 原始 payload → 物件儲存，保存90天（第4行）。
- 支援人員 → 管理主控台 → 儲存資料（第5行）：人員存取保存的內容。

Redis、資料庫、儲存桶的驗證、權限及網路邊界細節均無此證據。

下表逐項考慮 STRIDE；編號是**條件式威脅假設**，「—」表示設計未描述足以支持該類威脅的行為，不代表已有防護。

各假設及對策：

1. **冒用**：付款商驗證未定（第6行）；主控台身分控制亦未交代。若無可靠驗證，可能接受偽造請求或讀取者。於各入口驗證身分；後續以偽造、過期及重放請求遭拒的測試確認。
2. **竄改**：原始資料跨越上述流程（第2–4行）。若缺完整性、格式及業務驗證，可能造成錯誤對帳或保存失真。入口與 worker 各守其驗證邊界，並驗證重複事件不會重複入帳。
3. **否認**：多階段處理與人員讀取已明示，但稽核設計缺失於文件。若無關聯紀錄，可能無法追溯事件及讀取者。建立事件識別與受保護稽核；以端到端追溯案例確認。
4. **洩漏**：payload 的敏感內容及各層讀取權限未知。若包含敏感資料且權限過寬，可能洩漏。先分類、最小化保存與遮罩，再驗證未授權讀取遭拒及90天刪除。
5. **阻斷**：公開入口會排隊並保存資料。若無大小、速率及容量限制，可能耗盡資源。設限流、背壓與處理預算；以隔離負載測試確認。
6. **提權**：worker 使用正式資料庫憑證；支援人員可讀 payload。若輸入可決定非預期操作，或讀取授權不足，可能越權。限制 worker 操作及資料庫權限、限定人員可讀範圍；以負向授權測試確認。此處不推定存在程式碼執行能力。
