此版本確認有 SQL 注入與跨租戶讀取發票兩項漏洞，不能判定安全。

2. **判斷**

登入檢查建立使用者身分，卻未限制資料所屬租戶；路由也將請求參數直接拼入 SQL。兩條輸入至資料庫、再回傳資料的路徑均可由原始碼確認。

沒有找到底層資安技能、以基準做法完成。專案規則未指定工具，已安裝清單也無其他資安技能。

登入驗證本身不列為漏洞；現有證據顯示它會驗證 session，但不能取代租戶授權。未進行動態測試，亦未推定可寫入資料或執行系統命令。

3. **發現**

以下均綁定上述 SHA。

**F1：SQL 注入 — High**

- 主體：已登入使用者。
- 輸入：可控制的 `req.params.id`。
- 控制：缺少 SQL 參數化，直接插入引號內。
- 邊界：不可信請求資料成為 SQL 語法。
- 資源：`invoices` 資料。
- 結果：例如輸入 `' OR '1'='1` 可改變查詢條件，回傳不受指定 ID 限制的首筆發票。
- 證據：`src/routes/invoices.ts:2–6`。
- 分類：OWASP 2025 A05 Injection；CWE-89（識別碼未經外部確認）。
- 最小修正：以綁定參數傳入 ID。

**F2：缺少租戶授權 — High**

- 主體：租戶 A 的已登入使用者。
- 輸入：租戶 B 的有效發票 ID。
- 控制：查詢缺少 `tenant_id` 條件；登入 middleware 不做授權。
- 邊界：租戶 A 跨至租戶 B。
- 資源：B 的發票，包含金額與備註。
- 結果：查詢命中後，直接回傳他租戶發票。
- 證據：`src/routes/invoices.ts:2–6`、`src/auth.ts`、`db/schema.sql`。
- 分類：OWASP 2025 A01 Broken Access Control；CWE-639（識別碼未經外部確認）。
- 最小修正：查詢同時綁定 ID 與可信的 `req.user.tenantId`。
