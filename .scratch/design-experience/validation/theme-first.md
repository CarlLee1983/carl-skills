# design-experience 主題起手驗證

日期：2026-10-21。分支：`feat/design-experience-theme-first`。規格：[spec.md](../spec.md)；工單：[issues](../issues/)。

方法：每個情境由新的 general-purpose 代理獨立執行，只讀技能目錄（`SKILL.md` 與其指示的 references），不讀 docs、`.scratch`、README、GLOSSARY 或預期答案，不建立檔案、不使用瀏覽器；輸出第一則回覆與規則追溯。判定由主代理對照 `docs/design-experience/acceptance.md`，另判提案品質（來源與假設分開、建議附理由與取捨、開發者知道下一步）。未另開獨立評分代理。

## 01 設計師定位與進入模式判定

| 情境 | 夾具摘要 | 判定與觀察 |
| --- | --- | --- |
| E1 | Go REST API 診所預約，無前端、無品牌，README 寫 UI 規劃中 | 通過。判定主題起手並列出依據，以可修正理解呈現；不從 API 逐一推畫面。提案品質三項皆達。評估者指出主題起手與「Develop the visual language」的順序衝突（交 03）、風格訪談無指引（交 02）。 |
| E2 | React + Vite 庫存工具，有介面、無設計系統、功能半完成 | 通過。判定功能起手，明示功能未完成不影響判定；手寫 CSS 不視為固定視覺來源。 |
| R1 | Rust CLI，AGENTS.md 明訂 CLI-only，使用者授權概念探索 | 通過（回歸）。指出產品邊界、原型隔離於 repo 外、新增介面列為未決範圍。評估者推論 CLI 屬主題起手，條文未明寫——已補。 |
| R2 | Next.js 志工排班，功能完成，有文件化設計系統，主要使用者不明 | 通過（回歸）。判定功能起手、沿用設計系統；先形成 brief 並問角色。評估者指出新增介面不在既有設計系統涵蓋時無規則——已補「依介面分別判定」。 |

封裝：只複製技能目錄到暫存位置，`quick_validate.py`（`uv run --offline --no-project --with pyyaml python -B`）通過；`check_skill_links.py --references` 3 份 Markdown、4 處相對引用通過；`git diff --check` 通過。

## 02 主題起手的設計訪談

| 情境 | 夾具摘要 | 判定與觀察 |
| --- | --- | --- |
| S1 | 空 repo 只有攝影作品集 spec，無品牌；兩輪：第二輪「照建議，除了偏安靜高雅、不要太甜，沒有參考網站」 | 通過。spec 事實視為已定，第一輪只問限制、氣質詞對與品牌類專屬題；第二輪確認三項即結束訪談，不追問參考網站，轉入視覺處理。第一輪題數偏多（11 題）。評估者指出：品牌類缺攝影素材題、範例網站未查證、氣質詞歧義與「不再追問」的取捨、代表流程未在訪談中——已補。 |
| S2 | 無 repo、無規劃技能，「寵物用品購物網站」 | 通過。判定主題起手與電商，假設先做前台；只問會改變設計的產品題並標為假設，會員、訂閱、金流等列為未決，不產出規格。評估者指出無規劃入口時範圍交給誰未定、使用者自述類型是否算證據——已補。 |
| S3 | Laravel 茶葉電商，`/api/shop` 與 `/api/admin`，無前端 | 通過。依訊號分成前台（電商）與後台（功能型）分開訪談，先問先做哪個；資料缺口標為「需新增資料／契約」，不捏造能力。評估者指出回合順序是否為依賴、兩介面的 SESSION 結構——已補。 |

三個情境皆指出主題起手與「Develop the visual language」的順序衝突，交 03 處理。依評估修正為措辭補強，未重跑情境。技能目錄內沒有寫死的規劃技能名稱（`grill` 出現 0 次）。

封裝：隔離副本 `quick_validate.py` 通過；`check_skill_links.py` 4 份 Markdown、5 處相對引用通過；`git diff --check` 與新檔空白檢查通過。

## 03 視覺處理提前、混搭與品味基線

| 情境 | 夾具摘要 | 判定與觀察 |
| --- | --- | --- |
| T1 | 主題起手攝影作品集，訪談完成，「好，開始做吧」；允許寫入暫存設計目錄 | 通過。產出 3 個編號、附概念的 style tile，共用暫定手機版面並標明非結構提案；2 測「高雅」較濃讀法、3 測「真誠」；下一步才在選定處理中比較結構。代理無瀏覽器，標為視覺未審。主代理以 Playwright 1440px 實際開啟：三處理差在字體、表面深度與照片處理，不只換色；圖示為 inline SVG（13 處 `<use>`），掃描無 emoji、無文字箭頭；console 只有 favicon 404。 |
| T2 | 主題起手茶葉電商，已交付處理 1–3，回「1 的字體和留白，配 3 的顏色」 | 通過。記錄各部分來源、合成新處理並計畫截圖檢查一致，原 1–3 保留；底色歧義列為假設題。評估者指出合成編號與未指名維度繼承未定——已補。 |
| T3 | 功能起手 Vue 請假系統，設計系統與 Heroicons 固定，B 已選，做可點原型 | 通過。說明視覺由設計系統固定、不另做處理；以 Heroicons outline 經 SVG helper 繪製圖示（18 處），掃描無 emoji、無文字箭頭；狀態與恢復路徑完整，驗證標為部分。主代理以 Playwright 1440px 開啟確認圖示與版面。圖示路徑憑記憶寫出，代理已在 SESSION 標註。 |
| R3 | 功能起手，A／B／C 已比較，回「A」（回歸） | 通過。記為結構選擇、理由「未陳述」、不視為定稿；接著做以數字編號的 2–3 個視覺處理。評估者指出既有手寫樣式是否算視覺來源——已補「不算」。 |
| R4 | 功能起手，處理 1、2 皆「太普通，像模板」（回歸） | 通過。保留結構 B，提出概念更強的 3、4、5，字體、密度、表面與圖示皆不同；附可略的澄清題。評估者指出新一輪編號規則未定——已補「接續下一個未用編號」。 |

封裝：隔離副本 `quick_validate.py` 通過；`check_skill_links.py` 4 份 Markdown、5 處相對引用通過；`git diff --check` 通過。
