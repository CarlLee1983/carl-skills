# D8 dbcli（CLI 邊界）第二輪評審

**總判定：大致通過。** 進入模式判成改善、以重建的終端逐字稿當現況、指出 Non-goals、把 GUI 概念隔離成另一條主題起手軌道、「加進專案」不自行開工，這些都做對了；三個 style tile 的畫面品質也比第一輪扎實，設計師自稱的檢查大多與評審截圖一致。剩下的問題有兩個：邊界內的終端改善被設計師自己建議延後，排在範圍外的 GUI 概念之後，從頭到尾沒有做出任何終端逐字稿原型；概念軌依技能先跑完整輪風格板，使用者只選了視覺就要求「加進專案」。

判準：worktree `de-drills` 的 `skills/design-experience/`（SKILL.md 與 references）及 `docs/design-experience/acceptance.md`，以及 `drills/PERSONAS.md` 的 D8 觀察行。

## 畫面品質發現（評審自己截圖，judge-shots/）

用 Playwright 1.56.1 Chromium，在 1280×950 截三個處理的淺色與深色，處理 2 另截全頁與 1024×768；也用腳本量了每個文字節點的對比與字級、橫向溢出和鍵盤焦點。

- 已確認與設計師一致：1280 與 1024 寬都沒有橫向捲動；三個處理淺深色的所有可見文字都達到 AA（腳本以祖先背景估算，含白字紅底的錯誤卡）；數字用 tabular 並靠右；狀態用形狀加文字（方塊／圓點、空心環）；權限一律附文字「唯讀 read-only」，第一輪「權限只靠色點」的問題已經不存在。
- 深色模式焦點（設計師記為未檢查）：評審查過，處理 1、2 主要按鈕的 2px 焦點框都看得到（t1-dark-focus.png、t2-dark-focus.png）。
- 匯出進度：顯示「已寫出 182,400 / 約 1,204,000 列・已執行 1 分 12 秒」，進度條寬度與數字一致（15%），而且標為範例，不算假進度。第一輪那種長得像進度條的電平表已經沒有了。
- 字級（部分，設計師記為通過）：處理 1 的字級是 20/16/14/12，畫面上 12px 的文字節點有 40 個、14px 有 83 個，16px 只有 13 個。表頭、側欄 metadata、結果統計都是 12px，比 16px 內文低兩階；taste-baseline Type 節只允許密集表格與次要 metadata 低一階。處理 2（16/14）與處理 3（16/15/14）沒有這個問題。
- 字體角色（觀察，不判失敗）：三個處理都把等寬字用在欄位名、時間戳、連線位址，不只用在 SQL。這可以算資料內容的呈現，但已經接近第三種字體角色，交接時值得寫清楚規則。
- 處理 3 的「結果」分頁標籤只是裝飾，沒有分頁行為（原型 L166）。設計師已揭露，但它看起來可以點，正式化之前要決定刪掉或做成真的分頁。
- 首屏：1280×950 時，錯誤與匯出兩個狀態樣本都在摺線以下，設計師沒有宣稱它們在首屏內，不算偏差。

## 設計師執行偏差

1. 邊界內的軌道被延後，而且恢復條件被悄悄改掉。R1 承諾的終端 transcript 方向從沒做出來，這是設計師自己建議延後（Q13 a）的結果。到了 R5（L143）與 SESSION L38，恢復條件又從「GUI 選定方向後」變成「GUI 最後不做才恢復」，使用者沒有同意過這個改動。CLI 軌也沒列在 SESSION 的「未決事項」節（artifacts.md L35）。
2. 基線自查有一處不實：處理 1 的字級記為通過，但 metadata 用 12px，比內文低兩階。「表面」那一節沒有實際評估。
3. 小偏差：P3 標了兩個層級；Q10 的取捨軸大多只有一端附例子；R5 的入口用相對路徑。

## 限制

- 只依 transcript、SESSION、原型與評審自己的截圖判定，沒有看到設計師實際跑 impeccable 的過程。本輪 work/ 沒有 `.impeccable/` 目錄，第一輪那種可能對外連線的疑慮這次沒有證據。
- 對比是腳本以祖先背景色估算的，沒有處理半透明疊色；字級統計只算 `.app` 內的文字節點，不含頂部的比較列。
- 平台約定是 1280 以上的桌面寬度，評審只多看了 1024，沒有看窄螢幕。
- 使用者的回應來自腳本，不是真人試用，所以沒有可用性證據。
