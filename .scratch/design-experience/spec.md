# design-experience：主題起手與設計訪談

Status: ready-for-agent

日期：2026-10-21。來源：本次 `grill-with-docs` 訪談（Q1–Q20 全數依建議定案）與[設計訪談研究](research/style-interview.md)。用語以 `GLOSSARY.md`「設計探索」一節為準。

## Problem Statement

Carl 希望 design-experience 像一位產品設計師／UI/UX 設計師：接收模糊的想法與資訊，整理後提案給開發者。現行技能只在「功能大致完成、介面需要起點」時觸發，開場就讀 repo 形成 brief，再先比較結構方向、後做視覺。

當工作從一個主題開始（例如「做一個個人官網」「做一個購物站」），沒有既有介面可讀，技能既不會被觸發，也不會主動釐清風格。Carl 個人官網的實際紀錄證實這點：產品範圍由 grill 訪談確定，design-experience 只做了 A／B／C 結構比較；深色技術感與溫暖編輯風的比較，是 Carl 自己提出才補上的。風格靠使用者主動開口，而不是設計師引導。

此外，現行回饋表只處理方向層級的回覆（選 B、太普通），沒有「指著某個元素逐步微調」的循環；喜好與可用性也沒有分開詢問。

## Solution

design-experience 定位為產品設計師／UI/UX 設計師，依**進入模式**決定開場順序：

- **主題起手**（沒有既有介面，也沒有品牌或設計系統；只有後端也屬此類）：先依產品類型用輪次格式訪談，問清讀者與主要行動、氣質與硬性限制；接著做 3 個 style tile 形式的**視覺處理**以截圖比較，選定後所有**結構方向**套用它再比較；之後進入原型、細節微調與定稿。
- **功能起手**（已有介面或固定視覺來源）：維持現行先結構、後視覺的流程。

兩種模式共用 SESSION、回饋、定稿與交接。每個階段的產出都是可交給開發者的提案：區分有來源的判斷與假設，建議附理由與取捨，開發者知道下一步而不需重問。

## User Stories

1. 身為只有主題想法的開發者，我想讓設計技能在沒有介面時也被觸發，讓我不必先寫完功能才開始設計。
2. 身為開發者，我想讓技能依「有沒有既有介面或視覺來源」判定進入模式，讓有規格但沒有介面的專案也走主題起手。
3. 身為只有後端的專案擁有者，我想讓技能把我的專案視為主題起手，讓它從風格開始，而不是從 API 逐一畫畫面。
4. 身為已有介面的開發者，我想維持先結構、後視覺的流程，讓既有的設計工作方式不被打亂。
5. 身為開發者，我想讓技能先把它的判定（進入模式、產品類型）寫成可修正的理解，讓我能在它往下做之前糾正。
6. 身為開發者，我想讓訪談以輪次進行、每題編號並附建議答案，讓我能一次回覆「Q1 是、Q3 改 b」。
7. 身為開發者，我想讓訪談只問會改變設計的問題，讓我不用回答無關的問卷。
8. 身為做購物站的開發者，我想被問到商品如何被找到、圖片的角色與促銷版位，讓設計針對電商的真實取捨。
9. 身為做官網或品牌頁的開發者，我想被問到信任靠什麼建立與競品差異，讓設計傳達正確的定位。
10. 身為做後台的開發者，我想被問工作情境（看到就處理或之後再分析）與資訊密度，而不是一長串氣質形容詞，讓介面以效率為先。
11. 身為做內容站的開發者，我想被問掃讀與資訊前置的需求，讓閱讀體驗符合內容型態。
12. 身為前後台同在一個專案的開發者，我想讓技能把兩個介面分開訪談，讓相反的氣質與密度答案不互相稀釋。
13. 身為不懂設計用語的開發者，我想用對立詞對加兩端範例網站來表達偏好，讓我不必憑空說出「想要什麼感覺」。
14. 身為開發者，我想讓技能從我的取捨推導出 2–3 個氣質形容詞並請我確認，讓視覺處理之間有可辨識的差距。
15. 身為開發者，我想在讀者與主要行動、氣質形容詞、硬性限制三項確定後就結束訪談，讓訪談不無限延長。
16. 身為沒時間回答每題的開發者，我想讓未回答的項目被標為假設並繼續往下，讓工作不被卡住。
17. 身為可選擇提供參考網站的開發者，我想提供參考與反參考，但不被當成必填門檻。
18. 身為開發者，我想看到 3 個附一句概念的視覺處理，以 style tile 形式呈現真實內容的 hero、代表元件、字級階層與色彩角色，讓我比較的是視覺語言而不是版面。
19. 身為開發者，我想以截圖比較視覺處理，讓我看到的是實際畫面而不是描述。
20. 身為開發者，我想說「1 的字體配 3 的色彩」，讓技能合成新的視覺處理並截圖檢查概念仍一致。
21. 身為開發者，我想讓視覺處理用 1／2／3、結構方向用 A／B／C 編號，讓「選 B」不會有歧義。
22. 身為開發者，我想在選定視覺處理後，看到套用該處理的結構方向比較，讓結構取捨在真實風格下判斷。
23. 身為開發者，我想指出某個元素要改，讓技能只改那部分並附改前／改後截圖，讓我能一步步收斂細節。
24. 身為開發者，我想讓每次細節微調在 SESSION 留一行變更紀錄，讓之後的代理知道改過什麼。
25. 身為開發者，我想讓技能在回饋時分開問「喜不喜歡」與「做主要動作時哪裡卡住」，讓喜好不被誤當成可用。
26. 身為沒有安裝規劃技能的使用者，我想讓技能自己問最少量的產品題，並把答案標為設計假設，讓技能在任何環境都能用。
27. 身為有專案規劃入口的使用者，我想在範圍明顯過大時被提醒走該入口，而不是被自動啟動，讓我保有啟動權。
28. 身為開發者，我想讓設計假設不被寫成產品規格，讓產品決策仍由規劃流程負責。
29. 身為接手的代理，我想讓 SESSION 記錄進入模式、訪談答案與假設、選定的視覺處理，讓我不必重新訪談。
30. 身為接手的開發者，我想收到區分來源與假設、附理由與取捨的提案與交接，讓我知道下一步要做什麼。
31. 身為重視品味的開發者，我想讓原型不用 emoji、不用文字小箭頭充當圖示，而用風格一致的 SVG 圖示，讓原型看起來像經過設計而不是範本。
32. 身為有既有圖示集的開發者，我想讓技能優先使用專案指定的圖示集，讓原型與產品一致。
33. 身為維護者，我想讓技能說明與 UI metadata 反映兩種進入模式與設計師定位，讓觸發與安裝說明一致。
34. 身為維護者，我想有可重跑的驗收情境涵蓋新行為，讓日後修改能回歸測試。

## Implementation Decisions

- **單一入口**：擴充現有 design-experience，不另開技能；沿用 ADR 0001／0002 的單一入口原則。維持由模型自動觸發，不設為只能人工啟動。
- **角色定位**：技能開頭說明它扮演產品設計師／UI/UX 設計師，把模糊資訊整理成提案交給開發者；後續各階段「完成條件」以提案可交付為準。
- **觸發描述**：description 改為同時涵蓋「從主題或概念開始介面設計（先訪談風格）」、「功能已有但介面需要起點」與「接續設計探索」，保留現有排除條件（單純 CSS 修正、依既定設計直接實作）。UI metadata 的簡述與預設提示一併改寫，不再預設「理解這個專案」。
- **進入模式判定**：依是否已有介面或視覺來源，不依功能是否完成。只有後端屬主題起手。判定與推斷的產品類型先以可修正理解呈現。
- **規劃入口的可攜寫法**：技能內不寫死任何規劃技能名稱，改稱「專案的規劃入口」。沒有入口時，技能只問會改變設計的產品題（讀者、主要任務、主要行動），答案在 SESSION 標為設計假設，範圍外問題列為未決，不撰寫規格。有入口且範圍明顯過大時，提醒使用者走該入口，不代為啟動。
- **訪談流程**（寫在主檔）：輪次格式、每題編號附建議答案；只問會改變設計的問題；結束條件為三項（一句讀者與主要行動、2–3 個氣質形容詞、硬性限制：品牌素材、平台、語言、深淺色），參考與反參考選填；未回答標為假設並繼續。
- **題庫**（新增獨立 reference，只在主題起手時讀）：四類產品（電商、品牌／官網／行銷、功能性產品／後台、內容／編輯）各自的設計關鍵題；從專案材料訊號詞推斷類型；前後台同專案分開訪談；氣質以對立詞對加兩端範例網站取捨並推導形容詞；後台縮短氣質題，改問工作情境與密度。內容依研究檔整理，標註推論部分，不放未查證的行動 App 類別。
- **視覺處理提前**：主題起手時，把現行「發展視覺語言」階段移到結構方向之前。做 3 個附一句概念、以數字編號的 style tile（真實內容的 hero、代表元件、字級階層、色彩角色），截圖比較；沿用既有的截圖審看與「只換色盤算同一個」規則。選定後所有結構方向套用它。功能起手的順序不變。
- **回饋表擴充**：新增視覺處理混搭（記錄取用部分、合成新處理、截圖檢查一致性）；「選 B／C」類回覆依編號系統區分結構方向與視覺處理；新增細節微調循環（只改指出部分、改前／改後截圖、SESSION 一行變更、不順手改別處）。
- **品味基線**（適用兩種進入模式的所有原型與視覺處理）：不使用 emoji，也不以 `→`、`›`、`↗` 等文字符號充當圖示或裝飾；按鈕、連結、導覽、清單標記與狀態等介面元素使用具設計感的 SVG 圖示。來源優先順序：專案視覺來源指定的圖示集，其次為成熟的開源圖示集，以 inline SVG 放入原型，不新增套件依賴。圖示的線寬、填色與尺寸屬於視覺處理的一部分，同一原型內保持一致。
- **喜好與可用性分開**：原型回饋固定另問「做主要動作時哪裡卡住」，與喜好分開記錄；不納入 Desirability Toolkit。
- **SESSION 欄位**：延續紀錄 reference 增加進入模式、訪談答案與假設（含產品類型推斷）、選定的視覺處理及混搭來源、細節微調變更紀錄。
- **不寫 ADR**：順序調整與進入模式皆可逆，且沿用既有單一入口原則，理由保留在本規格。
- **README**：技能說明配合新 description 改寫。

## Testing Decisions

- **單一切面：行為情境重跑**。每個情境由新的 general-purpose 代理獨立執行，只讀技能目錄（主檔與 references）加一段情境夾具，不讀 docs、`.scratch` 或預期答案。主代理對照驗收文件判定可觀察的通過條件。先例：`validation/visual-language.md` 的 F／V 情境。
- **判定兩層**：一是行為通過條件；二是提案品質——是否區分來源與假設、建議是否附理由與取捨、開發者是否知道下一步而不需重問。
- **新增驗收情境**：
  1. 只有主題、沒有介面：輪次訪談，問到三項即停，做 3 個視覺處理，選定後才比較結構方向。
  2. 沒有規劃入口：只問會改變設計的產品題，答案標為設計假設，不寫規格。
  3. 只有後端的專案：判定為主題起手。
  4. 使用者指出某個元素要改：只改該元素，附改前／改後截圖，記一行變更。
  5. 視覺處理混搭（「1 的字體配 3 的色彩」）：合成並截圖檢查一致性。
  6. 電商或後台主題：提問符合該類型的設計關鍵題，前後台同專案時分開訪談。
  7. 品味基線：產出的原型與視覺處理沒有 emoji，也沒有以文字箭頭充當圖示；介面圖示為風格一致的 inline SVG，專案有指定圖示集時採用它。
- **回歸既有情境**：「結構已選定、無固定視覺來源」改為功能起手限定並重跑；「選 A」「太普通」受編號規則影響，重跑確認。未受影響的情境沿用先前結果。
- **封裝檢查**（不算行為證據）：metadata 驗證、相對連結檢查、空白格式檢查；確認只安裝技能目錄時新 reference 的引用可用。
- 情境為模擬，不建立真實產品或發布；瀏覽器不可用時依技能既有規則標記部分驗證。

## Out of Scope

- 行動 App 的專屬題庫（缺可靠來源，待有實際需求再補）。
- Desirability Toolkit 等量化喜好工具。
- 產品範圍規劃與規格撰寫（屬專案規劃入口）。
- 正式實作、建立正式網站或發布。
- 自動安裝或呼叫外部設計技能；collaboration reference 的候選表不在本次調整範圍。
