規格：[spec.md](../spec.md)。本工單先由使用者直接提出並實作，之後以 `grill-with-docs` 拷問（Q1–Q10 全數依建議定案），決策記在下方；用語見 `GLOSSARY.md`「設計探索」一節。

## 使用者故事

身為對目前 UI／UX 不滿意的開發者，我想讓設計技能以問答方式協助我釐清哪裡不好，再提出改善方案與原型，讓我不必自己先說清楚問題才能開始改。

## 決策

- 新增第三種進入模式**改善**：已有介面，且使用者的請求是改善它（不滿意），而不是替新功能設計介面。功能起手的定義補上「有功能需要介面設計」以區分。
- 改善前先截下目前畫面，固定標為**現況**（不使用 baseline 一詞，避免與既有的 taste baseline 混淆）；現況不佔方向字母或視覺處理編號。
- 診斷訪談沿用主題起手的輪次格式；題庫、自我檢視（Nielsen 十項啟發式＋品味基線）、問題分層與現況比較放在新 reference `improvement.md`，只在改善模式讀取。
- 問題清單附編號（P1…）、層級、來源（使用者／使用者的回報／代理檢視）、嚴重度；代理檢視屬專家檢視，證據等級低於真人試用。
- 依層級分流：細節 → 細節微調；視覺語言 → 在現有結構上做視覺處理；結構 → 結構方向；流程 → 流程原型。跨層時建議由深到淺處理，讓使用者可調整。
- 每個提案與現況並排，標明處理的問題編號與重新學習成本；必須保留的部分不動。
- 改善模式只由使用者表達不滿觸發；技能自認既有畫面不佳時，替新功能設計仍走功能起手，舊畫面問題只列為提案。
- 使用者只描述某元素的問題時屬細節層，截下現況後直接進細節微調；直接指定修法屬單純 CSS 修正，不啟動技能。
- 改善先前以本技能定稿的設計時，接續原 SESSION，現況取實際上線畫面，上線與定稿的落差列入問題清單。
- 代理自我檢視在第一輪診斷即提出，標為專家檢視。
- 既有條文缺口另開[工單 06](06-existing-wording-gaps.md)。
- 不寫 ADR：新增模式可逆，沿用單一入口原則；三項門檻皆未達。

## 驗收條件

1. 行為情境：使用者對現有介面不滿意時，判定為改善模式並附依據，先處理現況，再以輪次診斷訪談，不在診斷前直接提出重新設計。
2. 行為情境：含糊抱怨時提出 2–3 種具體解讀；代理檢視與使用者回報分開記錄。
3. 行為情境：診斷完成後，問題清單完整、依層級分流，提案與現況並排並保留必須保留的部分。
4. 回歸：替尚無畫面的新功能設計介面時，仍判定為功能起手。
4a. 行為情境：只指出某元素的問題時直接進細節微調；指定修法時不啟動技能。
4b. 行為情境：改善先前定稿的設計時接續 SESSION，現況取上線畫面，落差列為問題。
5. 封裝檢查通過；維護驗收文件與 README、UI metadata 反映新模式。
