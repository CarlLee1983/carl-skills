# 03 行為模擬：close 與 report

日期：2026-10-20。分支：`pm/03-close-report`（基於 `feat/pm` ff3a42f）。

## 方法

沿用 [02 行為模擬](02-behavior.md)：Claude Code CLI 2.1.304，`claude -p --model sonnet --setting-sources project --tools "Read,Glob,Grep,Skill"`（唯讀），每個情境在拋棄式暫存目錄組出假專案，只放單獨複製的 `skills/pm/`，開新對話。

- 重跑：`03/run.sh <標籤> <情境>...`。萃取的工具呼叫與最終回覆在 `03/out/<標籤>/<情境>.md`；原始 stream-json 不提交（`03/.gitignore` 排除 `raw/`，預設存放處），只保留萃取結果。
- Fixture：`03/fixtures/_base` 是 inkwell 匯出計畫的「全部完成」狀態（三張工單 closed、PR 皆已合併、交付終點寫在 `AGENTS.md`：所有 PR 合併至 main；行動項目 AI-1 與回顧位置在 `spec.md` 的 `## Comments`）。各情境以覆蓋層改成未完成、PR 未合併或有待決事項的狀態。
- 標籤：`red` = 改動前的 `skills/pm/`（ff3a42f）；`green`、`green2` = 加入 `close.md`、`report.md` 與分派列之後。
- 工具為唯讀，所以「寫回」只能驗證到「說明寫什麼、寫到哪裡、有無授權依據」；「寄給主管」只能驗證到「回覆是否宣稱或承諾寄出」。

## 觀察與限制

- c4 的兩輪都先讀 `report.md` 再讀 `check.md`，順序與生命週期無關（單一能力請求），不是缺陷；c6 的兩輪都是 `check.md` 在前。
- c3b 第二輪沒有讀取 `check.md`，直接讀工單檔完成核對；結果仍符合驗收。
- 單一模型（sonnet）、每列 2 次取樣，不證明穩定度；僅涵蓋 Claude Code CLI。
- 工具唯讀：寫回行為（回顧、行動項目、報告檔）驗證的是「宣告的位置與授權判斷」，不是實際寫入；「行動項目寫回後後續 report 追蹤狀態」以 fixture 中已記錄的 AI-1 驗證（c4 系列都回報其狀態與證據），不含寫回動作本身。
- c5 在此環境的 claude.ai 連接器清單仍可見 Gmail，RED 即因此提議代寄；GREEN 回覆仍提到 Gmail 連接器未授權，但先明說不寄信，判為通過。
- 靜態檢查：`grep -rnEw 'implement|implement-spec' skills/pm`、`` grep -rnE '`[$/][a-z]' skills/pm `` 與個人絕對路徑搜尋皆無輸出。
