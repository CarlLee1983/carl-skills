# design-experience：參考來源（目標稿與參考網站）

Status: ready-for-agent

日期：2026-10-23。來源：本次 `grill-with-docs` 訪談（Q1–Q16 全數依建議定案）。用語以 `GLOSSARY.md`「設計探索」一節為準，本次新增**參考來源**、**目標稿**、**參考網站**三個詞條。前一份規格見 [design-experience 主題起手](../design-experience/spec.md)。

## Problem Statement

Carl 常帶著兩種素材來找設計技能。第一種是一張圖，多半是 AI 生成的 UI 版型，意思是「我想做出這個」。第二種是一個網址，意思是「我喜歡這個網站的設計」。

現行 design-experience 只依「有沒有既有介面或視覺來源」與「是不是要改善」判定進入模式，沒有處理使用者帶來的素材。結果有三種失誤：

- 生成圖被當成定稿照抄，裡面的亂碼文字、只在單一尺寸成立的排版、缺少的空白或錯誤狀態、專案根本沒有的資料與能力，都原封不動進了原型。
- 生成圖被當成一般靈感，技能照常訪談、照常做三個視覺處理，使用者已經用圖回答的問題又被問一次。
- 網址只在訪談的選填「參考與反參考」題出現。技能不會拆解使用者到底喜歡那個網站的哪些地方，也沒有規則限制可以沿用到什麼程度；對方的品牌、圖像與文案可能直接被搬過來。

## Solution

使用者帶來的圖片或網址統稱**參考來源**，可以附加在主題起手、功能起手、改善任一種進入模式上，只改變該模式裡部分步驟的做法；三種進入模式的定義不變。技能依使用者意圖（不看媒介）把參考來源分成兩類，意圖不明時以可修正理解提出：

- **目標稿**：使用者想做出來的東西。技能先做可行性審查，逐項提出照做、改做法、刪除或待產品決定的取捨，再做成可試用的原型，與原圖並排比較。
- **參考網站**：使用者喜歡、只取其屬性的網站或截圖。技能拆成 5–8 個屬性，請使用者逐項標「要／不要／無所謂」，再用 2–3 個採用程度不同的視覺處理，在自家代表畫面上與參考網站並排比較。

多個參考來源以 R1、R2…編號。他人的實際產品被當成目標稿時，改以參考網站處理。工具不足時有明確退路，並沿用既有的證據層級。

## User Stories

1. 身為帶著生成 UI 圖的開發者，我想讓設計技能在我貼圖時被觸發，讓我不必先把圖翻譯成文字需求。
2. 身為開發者，我想讓技能判斷我的圖是「想做出這個」還是「只是喜歡某些地方」，讓它用對的方式處理。
3. 身為開發者，我想讓技能在判斷不出意圖時先把它的理解寫出來讓我改，讓它不會在錯的假設上做完一整輪。
4. 身為開發者，我想讓判斷看我的意圖而不是媒介，讓我丟網址說「做成這樣」或丟截圖說「喜歡它的配色」都被正確理解。
5. 身為帶目標稿的開發者，我想看到逐區塊的可行性審查，讓我知道圖上哪些東西專案根本做不到。
6. 身為開發者，我想讓審查指出圖上有、但專案沒有對應能力或資料的內容，讓原型不承諾不存在的功能。
7. 身為開發者，我想讓審查找出生成圖常見的瑕疵（亂碼文字、做不出來的版面、只在單一尺寸成立的排版、缺少的空白／載入／錯誤狀態、假的資料密度），讓我不把生成時的偶然當成設計。
8. 身為開發者，我想讓審查用品味基線檢查目標稿，讓圖上的對比不足或字級混亂不被照搬。
9. 身為開發者，我想讓每個審查發現附上照做、改做法、刪除或待產品決定的取捨與理由，讓我可以逐項同意或推翻。
10. 身為開發者，我想讓「待產品決定」的項目留給規劃入口，讓設計技能不越權決定產品範圍。
11. 身為開發者，我想拿到依取捨做成、可試用的原型，與原圖並排，讓我用同一個任務比較兩者。
12. 身為開發者，我想清楚看出原型和原圖哪裡不同、為什麼不同，讓我知道每一處改動在解決什麼。
13. 身為沒有介面、只有生成圖的開發者，我想讓訪談只問圖回答不了的問題（讀者與主要行動、硬性限制、圖上哪些是真的想要的），讓我不重複回答圖已經說明的事。
14. 身為開發者，我想讓技能從目標稿推導氣質形容詞再請我確認，讓訪談的完成條件仍然成立。
15. 身為開發者，我想讓取捨後的目標稿直接成為結構方向 A 與視覺處理 1，讓技能不為了湊滿三個而做我沒要的方案。
16. 身為開發者，我想讓技能只在審查發現結構或視覺問題時，針對那個問題提出替代方向或處理，讓替代方案有存在的理由。
17. 身為已有品牌或 token 的開發者，我想讓專案的視覺來源優先於目標稿，讓一張生成圖不會悄悄改掉品牌。
18. 身為開發者，我想在目標稿與視覺來源衝突時看到「照目標稿」與「照來源」並排，讓我自己決定要不要放棄來源。
19. 身為對現有介面不滿、帶了目標稿的開發者，我想讓技能仍先截下現況，讓目標稿有比較的基準。
20. 身為開發者，我想讓目標稿在改善模式裡被當成一個提案，標出它解決了問題清單上哪些編號，讓我看出它是否真的處理了我的不滿。
21. 身為開發者，我想讓技能指出目標稿與必須保留的項目之間的衝突，讓現有使用者依賴的東西不被一張圖蓋掉。
22. 身為改善模式的開發者，我想讓目標稿已經回答的診斷問題被跳過，讓診斷訪談縮短。
23. 身為喜歡某個網站的開發者，我想讓技能把它拆成 5–8 個屬性並附截圖區域，讓我能指出我到底喜歡什麼。
24. 身為開發者，我想逐項標「要／不要／無所謂」，讓回饋精準又不必用設計術語。
25. 身為開發者，我想看到 2–3 個採用程度不同的視覺處理，套在我自己的代表畫面上，與參考網站並排截圖，讓我選擇要像到什麼程度。
26. 身為開發者，我想讓之後的回饋沿用既有的編號與回饋表（選 2、1 的字體配 3 的色彩、太普通），讓我不用學新的回覆方式。
27. 身為開發者，我想讓技能量測參考網站的字級比例、間距尺度與圓角，當成重組自家 token 的起點，讓參考可以落到實作。
28. 身為開發者，我想讓技能不沿用對方的 logo、圖像、文案與品牌色組合，讓我的產品不冒用別人的品牌。
29. 身為開發者，我想在參考網站用了商用字體時拿到字型名稱與替代選項，讓我不誤用沒有授權的字體。
30. 身為主題起手、帶參考網站的開發者，我想讓「要」的屬性成為氣質形容詞的依據，讓氣質回合有具體依據可以推導。
31. 身為開發者，我想讓屬性標記取代訪談原本的「參考與反參考」題，讓同一件事不被問兩次。
32. 身為一次帶了好幾張圖或好幾個網址的開發者，我想讓每個來源有穩定編號 R1、R2，讓我能說「R2 的導覽」。
33. 身為開發者，我想讓不同來源在同一屬性上的衝突被列成一題問我，讓技能不自行把密與疏平均成不倫不類的中間值。
34. 身為開發者，我想混用目標稿與參考網站（「照這張圖做，但配色像這個網站」），讓我能組合不同來源。
35. 身為開發者，我想讓「做成跟 Stripe 首頁一模一樣」被改以參考網站處理並說明原因，讓我不在不知情下做出仿冒品。
36. 身為開發者，我想讓帶著他牌 logo 或名稱的生成圖先移除品牌元素再審查，讓原型不夾帶別人的商標。
37. 身為開發者，我想讓目標稿是我自己的設計或生成圖時照常處理，讓冒用規則不誤傷我自己的素材。
38. 身為在沒有瀏覽器環境下的開發者，我想讓技能改用文字擷取抓結構與 CSS 線索並請我補截圖，讓工作仍可進行。
39. 身為開發者，我想讓沒以畫面看過的參考網站在 SESSION 標為「未以畫面審看」，讓後續代理不誤以為屬性是看過畫面才定的。
40. 身為開發者，我想讓技能在圖片太小或被裁切時請我補完整尺寸，並把看不到的區塊在審查中標為「看不到」，讓它不自己腦補。
41. 身為接手的代理，我想在 SESSION 讀到每個參考來源的編號、類型、位置、屬性標記與可行性取捨，讓我不必重問使用者。
42. 身為接手的代理，我想讓參考圖與參考網站截圖存在設計目錄既有的 `references/` 子目錄，讓素材和 SESSION 一起被找到。
43. 身為開發者，我想讓交接寫明目標稿裡哪些項目被刪除或待產品決定，讓實作者不照原圖補回來。
44. 身為維護者，我想讓 reference 的細節放在獨立檔案、只在有參考來源時讀，讓沒有參考來源的流程不多付 context。
45. 身為維護者，我想讓新增情境有可觀察的驗收條件與獨立代理的驗證紀錄，讓這次變更能對應到 v1.1.0 的證據。

## Implementation Decisions

- **定位**：參考來源不是第四種進入模式。進入模式仍只依既有介面、視覺來源與改善請求判定；參考來源附加在判定出來的模式上，只改變部分步驟。決策記在 GLOSSARY「參考來源」詞條，不寫 ADR（可逆，三項門檻未達）。
- **意圖分類**：目標稿與參考網站依使用者意圖區分，與媒介無關；意圖不明時，把判定當成可修正理解寫出來，與進入模式的判定一起提出。
- **新 reference**：新增一份參考來源 reference，只在有參考來源時讀取。內容包括意圖判斷、目標稿可行性審查清單（三類：缺少能力或資料、生成瑕疵、品味基線）、四種取捨、與原圖並排的原型比較、參考網站的屬性拆解與三值標記、抽取邊界、多來源編號與衝突、冒用邊界、工具退路。
- **主流程**：主檔新增一個短節，說明何時讀新 reference，並在各模式相關步驟加入分支：
  - 主題起手加目標稿：訪談只問圖回答不了的部分，取捨後的目標稿成為方向 A 與處理 1，替代方案只針對審查發現的問題提出。
  - 主題起手加參考網站：「要」的屬性推導氣質形容詞，取代參考題；訪談完成條件不變。
  - 功能起手加目標稿：專案的視覺來源優先，衝突時「照目標稿」與「照來源」並排，沿用協作 reference 的偏好規則。
  - 改善加目標稿：仍先截下現況；目標稿視為一個提案，與現況並排，標出它處理的問題編號以及與必須保留項目的衝突；目標稿已回答的診斷題略過。
- **抽取邊界**：參考網站只抽屬性，量測值（字級比例、間距尺度、圓角等）只當成重組自家 token 的起點。對方的 logo、圖像、文案與品牌色組合不沿用；商用字體只記字型名稱與替代選項。
- **冒用邊界**：他人的實際產品被當成目標稿時，改以參考網站處理並說明原因；帶他牌 logo 或名稱的生成圖，先移除品牌元素再審查。
- **編號**：參考來源用 R1、R2…，與結構方向 A/B/C、視覺處理 1/2/3、問題 P1… 並存，跨輪次穩定。
- **觸發**：description 新增一個分支：使用者帶來 UI 圖或喜歡的網站。依 writing-for-agents，一個分支只寫一個觸發。
- **SESSION**：artifacts reference 新增「參考來源」欄位（編號、類型、位置、屬性標記、可行性取捨、是否以畫面審看）；交接增列目標稿中被刪除與待產品決定的項目。素材存在既有的 `references/` 子目錄。
- **周邊同步**：UI metadata 的簡述與預設提示、維護驗收文件（含 reference 數量與本機相對連結數）、範例文件新增兩個情境的走法、README 的技能說明（若描述觸發範圍）。
- **版號**：依 ADR 0003 屬於新增能力與觸發，升 MINOR 到 `design-experience/v1.1.0`；tag 與 Release 另行授權。
- **語言**：技能內文以英文撰寫；固定輸出文字、觸發語與領域詞（現況、目標稿、參考網站、「要／不要／無所謂」、「未以畫面審看」、「看不到」）保留原文。

## Testing Decisions

- **單一切面：行為情境重跑**。每個情境由新的 general-purpose 代理獨立執行，只讀技能目錄與一段情境夾具，不讀 docs、`.scratch` 或預期答案。主代理對照驗收文件判定可觀察的通過條件。先例：`.scratch/design-experience/validation/visual-language.md` 與 `improve.md`。
- **判定兩層**：一是行為通過條件；二是提案品質，包括是否區分來源與假設、建議是否附理由與取捨、開發者是否知道下一步。
- **夾具**：
  - 目標稿：一張刻意埋了瑕疵的生成風 UI 圖，以本機 HTML 渲染成 PNG。瑕疵包括亂碼文字、只在固定尺寸成立的排版、缺少的空白或錯誤狀態、專案不存在的資料欄位、對比不足的小字、帶他牌 logo 的區塊。夾具附上該圖對應的專案能力清單，讓「缺少能力」可以被判定。
  - 參考網站：一個本機起的 HTML 頁，有可辨識的字級比例、間距節奏與配色結構，排除外部網站改版與網路造成的變動。
  - 「做成跟 Stripe 首頁一模一樣」只用文字情境，不實際抓取。
- **新增驗收情境**：
  1. 主題起手加生成目標稿：判定意圖為目標稿；做出三類可行性審查與四種取捨；訪談只問圖回答不了的題；目標稿成為 A 加 1，替代方案只對應審查發現；原型與原圖並排。
  2. 功能起手、專案有品牌 token，目標稿風格不同：來源優先，「照目標稿」與「照來源」並排請使用者決定。
  3. 改善模式加目標稿：先截現況；目標稿標出處理的問題編號與必須保留項目的衝突。
  4. 參考網站：拆成 5–8 個屬性並附截圖區域，請使用者三值標記；之後的 2–3 個處理採用程度不同，套在自家畫面上與參考網站並排；不沿用對方品牌、圖像與文案。
  5. 「做成跟 Stripe 首頁一模一樣」：改以參考網站處理並說明原因。
  6. 多來源衝突（R1 密、R2 疏）：列成一題詢問，不平均。
  7. 意圖不明（「看看這張圖」）：以可修正理解提出意圖判定。
  8. 瀏覽器不可用的參考網站：改用文字擷取、請使用者補截圖，SESSION 標「未以畫面審看」。
  9. 被裁切的目標稿：請使用者補完整尺寸，看不到的區塊標「看不到」。
- **回歸既有情境**：只重跑受影響的部分，包括主題起手訪談（參考題被取代）、功能起手視覺來源衝突、改善模式截現況；其餘沿用先前結果。
- **封裝檢查**（不算行為證據）：metadata 驗證、相對連結檢查、空白格式檢查；確認只安裝技能目錄時，新 reference 的引用可以解析。
- 結果記在 `.scratch/design-experience/validation/reference-sources.md`，並在驗收文件的驗證紀錄段落連結。

## Out of Scope

- 網站案例頁：驗證完成後另開一件工作，依實際驗證結果寫。
- 打 tag 與發布 Release。
- 實際抓取第三方網站作為驗證夾具。
- 從圖片自動產生生產環境程式碼（image-to-code 仍屬協作能力，由協作 reference 選用）。
- 協作 reference 的候選能力表調整。
- 產品範圍規劃與規格撰寫（屬專案規劃入口）。
