# B1：備份與復原評估

開始時選定「備份健康」「PITR 目標覆蓋」「一次指定還原演練」的一項或多項，再固定必要主張。備份健康是分項摘要，不新增單一成功狀態。所有共用能力檢查、結果順序與執行責任依 [SKILL.md](../SKILL.md)。

## 1. 固定評估輸入

記錄資源識別、環境、引擎／完整版本、部署形態、參考時間與時區、指定備份／PITR 目標，以及新演練或指定歷史演練。資料／服務負責人確認 RPO、RTO、新鮮度、保留要求、證據時效與量測起訖；資料／應用負責人確認關鍵資料、業務不變條件與對應截點基準。另列有權批准者、人工執行者、證據交回責任人。

列缺口前，先逐項盤點已提供的基準確認者、截點、預期值／不變條件及實際比較結果。已指定、可追溯且符合時效的受控證據包若內嵌這些內容，直接核對並沿用；附有原件 reference 不代表只有引用、沒有基準內容。只請責任人補實際缺少或有真實性／完整性／適用性疑點的項目，不要求重交已有合格內容，也不把缺驗證結果誤列為缺基準。

缺政策、基準或可比較量測時保留觀察，將受影響主張記為 indeterminate；不否定其他已有充分證據的主張。來源或預定隔離目標身分不明時，停止受影響的查詢與人工變更執行交接，先依第 4 節交人確認身分。其餘安全且獨立的評估可繼續，但版本不支援仍停止整個流程。

## 2. 取得最低證據

| 主張 ID | 最低證據與判定 |
| --- | --- |
| `backup_exists` | 綁定對象的備份識別、種類、時間、完成／可用狀態。只有備份設定不足。 |
| `backup_freshness` | 已確認的新鮮度要求、可比較參考時間與實際備份時間。 |
| `backup_retention` | 已確認保留要求與實際涵蓋範圍；設定保留天數不代表實際覆蓋。 |
| `pitr_coverage` | 明確目標時間點／區間（若輸入 `pitr` 為 `null` 或未指定本次 PITR 覆蓋目標，須將未指定目標列為缺口並交由 `service-owner` 確認，不得直接將 `drill.sourcePoint` 歷史演練截點冒充為已確認的本次 PITR 覆蓋目標）、同一資源的可還原窗口、取得時間與適用性。完整目標須落在窗口內，邊界依來源語意。完整適用證據顯示在外為 not-met；窗口缺失、過時或矛盾為 indeterminate。不改目標，不宣稱已演練。 |
| `restorable` | 指定來源備份／截點、隔離目標身分、人工操作紀錄、還原結果與事先確認的必要唯讀驗證。平台 available、連線成功、口頭完成不足。充分的驗證失敗為 not-met，缺證據或矛盾為 indeterminate。 |
| `rpo` | 政策、事件／演練參考時間、可證實的資料復原點或足以判斷的界限、基準與計算。無法據界限判達標或超標為 indeterminate。平台窗口差距、max(updated_at) 或通用筆數不能冒充已證實的復原點。 |
| `rto` | 政策定義的起訖、時間戳及終點要求的驗證證據。輸出必須具體呈現可量測的還原作業耗時、驗證完成耗時與合計已知耗時（若起點時區不明或缺口，明確標記等待區段或完整政策 RTO 為無法判定，不能省略已知區段量測）；未驗應用恢復不能宣稱服務 RTO。 |

三個演練主張分別判定，不從平台成功推導。RPO 的時間戳或「已證實」標籤本身不是資料復原點證明；若該點由基準與驗證比較推導，須能取得基準、比較結果且比較成立。相依推導在必要證據齊全且比較成立後，也可構成合格證明，不因它不是獨立證據而否定。其他獨立合格證據則按其實際覆蓋判讀，不強制依賴同一個工具或檔案。來源 ID、時間、對象、受控位置及檔案雜湊須可追溯；只引用本次實際可取得且符合時效的證據。

## 3. 引擎與平台取證

先按所選主張列出需要的操作，再做 capability check；不為所有評估強制跑整張工具清單。只有必要的 SELECT／SHOW／metadata 才讀取引擎，既有合格人工證據可支援歷史評估。每次即時觀察記錄起訖、負載、逾時與列數預算；CLI 逾時不代表伺服器已取消所有操作。

| 引擎層 | 觀察族與限制 |
| --- | --- |
| PostgreSQL | 來源／還原目標身分、版本、recovery 狀態；適用 WAL／archive／slot 訊號；確認過的 schema、關鍵資料與業務不變條件。WAL 不證明備份鏈完整、可還原或 RPO／RTO。 |
| MySQL | 身分／版本、binlog 開關與保留、檔案／位置、適用 GTID，以及還原目標基準。binlog 訊號不等於 RDS PITR 窗口。 |
| MariaDB | 依自身版本與 binlog／GTID 語意取得同類觀察，不移植 MySQL 函式／欄位語意，不放行 CALL。 |

原生權限拒絕或查詢失敗是觀察缺口，不是物件不存在或備份不健康。CALL 因政策拒絕，所缺觀察為 indeterminate，交既有授權人員；`binlog retention hours` 不等於 RDS `BackupRetentionPeriod`。

RDS 平台層取得計畫內的備份／snapshot／可還原窗口、事件與相關紀錄，保持 AWS 與引擎權限證據分開。使用者未授權即時存取時，可評估既有可追溯資料，不自行取得更多存取。自管引擎訊號不支持平台備份鏈／還原主張，該平台層為 indeterminate。

## 4. 人工演練與清除 runbook

準備人工變更的執行交接（建立、還原、設定或清除）時，輸出必須逐項明列：**操作目的與影響、費用／敏感資料風險、安全停止方式、回復限制、執行時間窗、重試限制、必要唯讀驗證範圍與預算、人工執行者、證據交回責任人／方式／必要紀錄**。每項填已確認內容與依據，或列為執行前待確認缺口、責任人與解除條件；不適用項說明操作別理由，不能只補其中幾項便交接為可執行。即時觀察的預算依計畫包含起訖、負載、逾時及列數限制，不自行填數字；沒有計畫內 SQL 驗證的清除不因此新增查詢要求。清除另核對下列刪除範圍、證據保存、批准及重試條件。

以上欄位與下列來源／目標、計畫／環境一致性、隔離／存取限制及批准適用性核對一併成立，才具執行條件。只交接身分或批准等阻礙的解除時，不暗示其餘條件已齊。有效批准不單獨代表執行就緒，也不要求重複取得仍有效的批准；歷史證據缺口依第 5 節處理。

1. 人工建立／還原交接前，確認來源與預定隔離目標身分，並核對計畫版本、環境、批准資源與隔離範圍一致。尚未建立的目標可依預定名稱／識別及 account、region、環境確認，不要求先取得建立後才有的 ID；批准列出的資源不能自動填補尚未確認的目標身分。身分仍不明時，只交接身分確認，維持相關變更 blocked，不先執行再補身分。固定資料範圍及本次時間窗，確認避免正式流量誤接、不預期外連、存取限制，以及必要唯讀驗證與預算；隔離未確認也停止還原執行交接。
2. 列操作目的、人工執行者、影響、費用／敏感資料風險、安全停止方式、回復限制、重試限制及證據交回方式。指定有權批准角色與可接受的身分確認來源；只有姓名不足以證明資格。
3. 人工變更前核對有效批准：綁定計畫版本、環境／資源／操作、本次執行、時間窗、決定、批准者、條件與來源。缺失／拒絕／過期／撤回／範圍變更維持受影響步驟 blocked，交接解除條件。等待批准與已批准待人工執行分開記錄。
4. 指定人員執行建立／還原／設定。Skill 等待操作與驗證證據，再依既有權限執行已批准範圍內的唯讀驗證。批准不是執行完成，重試不得超出原批准。已開始的操作遇撤回，交人依安全停止方式處理，不能假設已回滾。
5. 人工清除前核對批准仍有效、目標／刪除範圍一致、授權涵蓋本次嘗試及必要證據已保存（即使還原尚未開始或因批准／能力受阻，只要輸入或計畫涉及清除／`cleanup`，交接也必須明列清除由指定人員執行、維持未就緒／受阻且不授權開始清除，並明列上述完整 runbook 準備缺口：操作目的與影響、費用／敏感資料風險、安全停止方式、回復限制、以及清除結果的證據交回方式與必要紀錄，連同四項清除前核對條件一併作為待指定責任人補齊的執行前阻礙）。同一有效批准若已涵蓋清除及本次嘗試，沿用即可；實質變更重新批准。由指定人員清除，Skill 不執行清除命令。
6. 清除失敗記錄殘留資源、原因、負責人與後續動作，明示未收尾。再次清除也是重試；交接執行前核對原批准的重試限制。未授權或額度已耗盡時，先交批准者取得涵蓋本次重試的有效批准，不能直接交接再次執行。恢復權限或批准尚未過期不增加重試授權；原批准仍涵蓋本次重試時才可沿用。清除問題不抹去已成立的歷史復原結論。必要證據保存失敗且無合格替代時，受影響主張 indeterminate；有替代則核對其適用性後判讀。

runbook 不包含正式流量切換、持續存取或排程。每次決定追加記錄，保留原批准、拒絕與撤回來源。

## 5. 歷史評估與交付

可選指定歷史演練，無須強制重做還原。結論限當次來源、截點、環境與驗證條件；另列證據目前可取得性、時效，以及引擎、金鑰、設定、資料範圍變更造成的適用性缺口。昨天成功不升格為今天可還原；舊結論也不因新缺口改成歷史失敗。

歷史目標已清除或不可取得時，先由指定證據責任人尋找當次既有驗證紀錄或合格受控替代；缺失時保留相關歷史主張 indeterminate，不要求直接重查已清除目標。需要重新建立／還原才能補驗時，另立人工計畫，確認目標、隔離、重試範圍與有效批准；新演練另記結果，不直接回填原歷史演練。既有紀錄取得與仍獲准的唯讀操作不等於重做還原，不因變更重試額度為零而一概禁止。

輸出主張、證據、限制、混合結果及人工交接。先核對已有內容，只將實際缺失、不適用或矛盾的內容列為缺口；未另讀引用檔不等於證據缺失，缺政策門檻也不否定已有合格量測。每項缺口寫受影響範圍、已有證據、缺少什麼、原因、解除條件與接手人，不要求人員重交已具備的合格證據。行為測試 PASS／FAIL、DBA 主張結果與真實環境覆蓋分開；正確判 blocked 可以通過行為案例，卻不證明資料庫主張 met。

## B4 驗收

必要行為類別：完整適用證據；備份存在但新鮮度／保留不符；PITR 內／外／邊界／缺失／過時／矛盾；平台成功但資料失敗／不足／矛盾；政策／基準／量測缺口；身分／隔離／批准停止；能力／版本停止；CALL／IAM／原生無權／查詢失敗；歷史適用性變更；清除／保存失敗；自管只有引擎訊號。

分支及交叉案例、三次新 session 與 F／L／R 證據要求以 [核准策略](https://github.com/CarlLee1983/dbcli/issues/254#issuecomment-6259263089) 為準。F 使用實際 Skill 與攔截工具，嘗試禁止操作也算 FAIL。完整 B1 另需三引擎各自管／RDS 共六組實證、每個 RDS 引擎快照還原及 PITR 人工演練、受限身分正反例與同候選人類驗收。未完成時保持候選版，不能由合成案例或 dbcli 測試補成實環境已驗收。
