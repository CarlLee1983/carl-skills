# B3：原生權限與生產變更治理評估與人工交接

遇到原生權限稽核、TLS／憑證稽核、指定變更（原生 DDL、原生帳號／角色／GRANT、TLS／憑證相關變更）的執行前準備或執行後驗證時使用本流程。先遵守 [共用能力、結果與證據規則](../SKILL.md)。完成條件是：固定範圍的每個必要主張都有判定、可追溯理由與缺口／接手人；只有全部事先選定的必要主張均為 `met`，才宣稱本次固定範圍內全部符合。就緒度、批准有效性及執行結果分開記錄；稽核通過不證明變更安全。

## 1．固定評估入口、輸入與責任

每次開始前從「原生權限符合基準」「TLS／憑證符合要求」「指定變更的執行前準備」「指定變更的執行後驗證」選一項或多項，事先固定必要子主張、對象、環境、時間／時區、適用條件、最低證據與不適用理由；未知不是不適用，未選項標「本次未評估」，不能事後移除失敗或缺證據的必要主張。

輸入記錄資源／連線及資料庫身分、引擎與確切版本、適用的儲存引擎、部署形態、評估帳號／角色／物件／客戶端範圍、取得時間與時區。變更另記計畫版本、目的、精確目標、操作類型及順序、預期差異、受影響依賴與指定事件；區分新觀察和歷史證據。

列缺口前，先逐項盤點已提供的基準／預算確認者、政策時點、預期值／不變條件及實際觀察。已指定、可追溯且符合時效的受控證據包若內嵌這些內容，直接核對並沿用；只請責任人補實際缺少或有真實性／完整性／適用性疑點的項目。

- **資料／服務負責人及安全責任人**確認期望權限與 TLS 基準：帳號用途、允許物件／操作、角色繼承與管理權限、例外及有效期限、TLS／憑證要求、證據範圍與時效。
- **變更負責人**確認鎖等待、操作／影響時間、查詢負載與觀察預算、停止門檻、復原要求及驗證基準。
- **資料／應用負責人**確認必要業務不變條件與服務恢復標準。
- 另列**有權批准者（如 `change-manager`，變更／修正計畫之批准權專屬於有權批准者，勿在交接中將 `change-owner`、`security-officer` 或執行者寫為批准變更者）、人工執行者及證據交回責任人**。

Skill 可提出建議，不自行套用通用達標秒數或把現況當基準。缺基準仍可盤點，無法比較的相關主張為 `indeterminate`，不抹去其他已充分證成的結論。

- **目標身分與資料庫名稱之取得**：優先自 `config.json`（或 `--config` 指定設定目錄內之連線設定，如 `connections.<name>.database`，例如 `"fixture"`）、評估輸入或連線定義中取得，不能僅看 `target` 物件欄位。只要連線設定或受控證據已提供資料庫名稱，就應直接沿用並在交接目標中具體列出（例如 `isolated-staging`、`rds:example:instance-b3`、資料庫 `fixture`、物件 `app.orders`），保留執行前連線身分核實即可；**嚴禁**將已存在於設定檔中的資料庫名稱錯報為「具體資料庫名稱待補」或「缺失證據」，不可製造不必要的交接阻擋。
- **嚴格忠實陳述基準（Fidelity to Baseline）**：陳述帳號權限基準時，必須嚴格依照 `baselines` 原始定義陳述允許物件、允許操作、允許角色等白名單範圍，**嚴禁擅自發明排他性授權途徑限制**（例如：基準僅列允許物件為 `app.orders`、允許操作為 `SELECT`、允許角色包含 `app_readonly_role`，切勿將其扭曲宣稱為「僅能透過 `app_readonly_role` 取得 `SELECT`」或「禁止直接 GRANT」等非基準明載的排他途徑限制）。忠實保留基準原貌，不額外新增政策。

引擎層涵蓋 PostgreSQL、MySQL、MariaDB 的自管與 AWS RDS 環境，由 dbcli 執行計畫內唯讀觀察。平台層僅涵蓋 RDS，不含 Aurora；自管及其他平台未涵蓋的平台層主張為 `indeterminate` 並交人，不因此否定可評估的引擎層主張。

變更治理僅涵蓋**原生 DDL、原生帳號／角色／GRANT，以及 TLS／憑證相關變更**；三類各有對應的前置、復原與驗證交接。大量 DML／資料回填、應用發布、通用主機維運及自管平台層操作不納入 v1。需要應用或客戶端配合時，記錄相依工作、責任與交回證據，不擴張成應用發布或客戶端部署工具。需要 `gh-ost`、`pt-online-schema-change` 等外部工具時，記錄適用性、限制與待補條件，交專家；不默認替換工具，不將完整外部工具 runbook 納入 v1，也不把外部工具缺口當作已具備執行條件。

Skill 準備 runbook、蒐證、判讀與唯讀驗證；變更、設定、重啟、終止連線／blocker、額外身分／寫入探測、復原及清理**一律由人按批准計畫執行，不因非正式環境而自動授權**。

## 2．有限觀察、可見性與引擎語意

以共用 requirement set 檢查 capability／contract 後，僅做已選計畫內的唯讀觀察。先核對實際引擎與版本語意，涉及表／視圖先 `blacklist list --format json` 與 `schema <qualified-object> --format json`，再執行 `query <sql> --format json`；SHOW／純函式不虛構 table schema（僅 `blacklist list --format json` 後 `query <sql> --format json`）。每次觀察有起訖、查詢負載與逾時預算；觀察達預算即停止該觀察，不自動延長。目標身分不明時停止對該目標查詢；版本不支援（`schemaVersion` 不符）停止整個工作流程。

蒐證只選必要欄位，**嚴禁讀取、保存或輸出密碼雜湊、認證字串、私鑰與其他非必要秘密**。敏感原始資料使用受控引用。

可見性不足時，保留安全且獨立的唯讀盤點，列出可見／不可見對象、欄位、時間及所需證據，交既有授權者補證。空集合、`NULL`、查詢失敗、原生無權、`blacklist` 省略或自動 `LIMIT` 截斷均不自動證明物件／權限不存在或全體符合；只看得到自身不代表全體。不得自行升權、改 profile、安裝 extension、取消 blacklist、或繞到原生客戶端。

| 引擎／領域 | 判讀時必須遵守的語意邊界 |
| --- | --- |
| PostgreSQL 權限與統計 | 核對直接 GRANT、role membership、`INHERIT`／`SET ROLE` 啟用語意、物件 owner、`PUBLIC`、管理／再授權（`ADMIN OPTION`／`WITH GRANT OPTION`）與 `pg_default_acl`（未來新建物件的預設權限）。非高權 session 查詢 `pg_stat_activity`／`pg_stat_ssl` 等系統視圖時，其他 session 部分欄位有可見性限制，查詢成功不等於取得全體完整觀察。 |
| PostgreSQL DDL 與索引 | 逐版本與操作判定鎖等級、資料重寫與交易回滾能力。`CREATE INDEX CONCURRENTLY`／`DROP INDEX CONCURRENTLY` 不可在交易區塊內執行，且建立失敗可能留下 `INVALID` 索引（`pg_index.indisvalid = false`），不把命令失敗當作未產生變更；必須驗證索引有效性與殘留，清理交人按批准計畫處理。 |
| MySQL 權限與 DDL | 核對直接 GRANT、角色指派、預設啟用角色（`mandatory_roles`／`activate_all_roles_on_login`／`DEFAULT ROLE`）、全域／動態權限、`WITH GRANT OPTION` 與系統 schema 存取。`SHOW GRANTS` 查看其他帳號需要 `mysql` system schema 的 `SELECT`，無該權限時不能當成通用替代。多數 DDL 會觸發 implicit commit；`CREATE`／`DROP TEMPORARY TABLE` 雖不觸發 implicit commit，但**仍不可由使用者 rollback**，不能寫成所有 DDL 一律 implicit commit，也不能反向推論未提交即可回滾。atomic DDL 只保證單一語句原子性，不等於使用者可回滾，多步 DDL 中途失敗會造成前序步驟已提交的部分完成狀態。 |
| MariaDB 權限與 DDL | 必須依 MariaDB 自身版本的角色（`SET DEFAULT ROLE`、角色繼承與啟用，語法與系統表不同於 MySQL）、權限、`ALGORITHM`／`LOCK` 支援矩陣及交易／DDL 語意核對，**不得直接移植 MySQL 的結果或假設相同語意**。多步 DDL 失敗同樣須重查實際已提交步驟與物件狀態，不宣稱整批已 rollback。 |
| RDS 平台與受管角色 | RDS 受管高權角色（如 `rds_superuser`、`rds_admin` 或平台預設管理角色）按引擎與實際可達能力判讀，不把角色名稱視為通用原生 superuser，也不忽視其高權影響。RDS 參數變更須區分平台要求值、套用狀態（如 `pending-reboot` vs `in-sync`／已套用）與引擎實際生效值；RDS 伺服器憑證／CA 識別、有效期、輪替及待套用狀態與客戶端信任分開判讀。 |

## 3．分項最低證據與判定界線

以下名稱可對應本次固定的 claim ID。使用者已給 ID 與定義時保留其對應，不改寫 ID、不事後移除不利或缺少證據的必要主張。結果 `claims` 只列事先固定的必要主張；未選項在未評估範圍說明。每項證據必須連結同一評估對象、時間、來源與可見範圍，不能將不同帳號、客戶端或時間的結果拼成不存在的完整快照。

依共用四態優先序判定：充分且無相關矛盾先判 `met`／`not-met`；有未解決相關矛盾為 `indeterminate`（優先於 `blocked`）；必要步驟因 capability 非 available 或等待人工批准／執行／身分確認而受阻為 `blocked`；其餘不足（含缺基準、缺平台／AWS CLI／唯讀 IAM、CALL 拒絕、原生無權、查詢失敗、可見性不足、執行後缺必要驗證、證據保存失敗且無合格替代）為 `indeterminate`。已充分證實的過度授權、門檻違規（如複製延遲超標）或其他 `not-met`，不被輔助查詢受阻或缺樣掩蓋。**充分證實違反就緒門檻優先於 blocked**：前置觀察若已在時效與預算內完整取得，且明確證實違反經確認的停止門檻（例如複製延遲 45 秒超標大於 5 秒預算），已構成不符合就緒條件的充分反面證據，依 ADR-0046 優先序 `change_readiness` 必須判定為 `not-met`（同時交接必須維持停止執行、受阻交接）；切勿因「停止執行交接」而將已充分證實的門檻違規改判為 `blocked`。`blocked` 僅適用於觀察因預算截斷未能取得完整數據、必要 capability 不可用、或等待前置身分確認／批准等步驟受阻致證據不足之情形。

| 主張（建議 ID） | 最低證據與分項界線 |
| --- | --- |
| 指定帳號／角色的權限符合基準（`account_privileges`） | 已確認的用途與預期權限基準、完整目標識別，以及適用的直接授權、角色成員／繼承／啟用關係、`PUBLIC`、物件擁有者、管理／再授權能力與預設權限。分清目前物件、未來新建物件与本次 session 的有效權限，不僅比較直接 GRANT。最小權限相對於經確認的用途與必要操作，不以「權限越少越合格」或通用清單替代需求；複雜語意超出可證明範圍時列缺口，不自稱完整有效權限分析器。充分過度授權或缺少必要授權為 `not-met`；缺基準、可見性不足或來源矛盾為 `indeterminate`。嚴格依照基準白名單中性陳述，嚴禁擅自發明排他性授權途徑限制。 |
| 高權限與例外符合要求（`privileged_exceptions`） | 適用的高權屬性、全域／動態權限或受管角色、影響範圍，以及安全責任人確認的例外批准、用途與有效期限。未獲准高權、超出核准範圍或例外已過期為 `not-met`；缺基準、缺有效期／例外紀錄或可見性不足為 `indeterminate`。 |
| 指定連線的 TLS 符合要求（`connection_tls`） | 同一連線／端點、時間、傳輸方式、適用的 TLS 協定版本與密碼套件等訊號，以及已確認政策要求。僅支持該連線或明確觀察窗內的指定集合，**不外推所有連線均符合**。明文或低於政策要求為 `not-met`；缺政策或觀察為 `indeterminate`。 |
| 伺服器／帳號的 TLS 強制政策符合要求（`tls_enforcement`） | 適用的生效設定（如伺服器強制 TLS、HBA／存取規則或帳號 `REQUIRE SSL`／`REQUIRE X509` 等）、覆蓋範圍；RDS 須同時對照平台要求值、套用狀態與引擎實際生效證據。僅支援 TLS 或本連線已加密，不等於拒絕非 TLS；要求值處於 `pending-reboot`、未生效或與引擎觀察矛盾不能判 `met`。充分證據顯示引擎生效值未強制（如 `rds.force_ssl=off`）或仍允許政策禁止的非 TLS 連線為 `not-met`；平台與引擎未解決矛盾、或僅有平台 pending 而缺引擎生效觀察／缺證據為 `indeterminate`。 |
| 指定客戶端的憑證與主機名驗證符合要求（`client_tls_verification`） | 該指定客戶端／驅動及版本的有效驗證設定（如 `verify-full`、信任 CA 來源、主機名驗證）與對應連線／重連成功證據。資料庫端加密訊號或 dbcli 自身連線不能單獨證明指定應用客戶端已驗證伺服器身分；客戶端停用驗證、不信任新 CA 或主機名驗證失敗為 `not-met`，缺指定客戶端證據為 `indeterminate`。 |
| RDS 憑證狀態符合要求（`rds_certificate_status`） | 同一資源的伺服器憑證／CA 識別、適用的有效期限、輪替與套用狀態，以及政策時點。CA 有效、伺服器憑證有效與客戶端信任分開判讀，不互相替代。過期、低於政策要求的 CA 或未完成套用依證據判 `not-met`／`indeterminate`。 |
| 指定變更的執行前準備就緒（`change_readiness`） | 指定變更計畫在指定時點具備全部必要前置證據、預算、復原方案、有效批准與執行交接條件。就緒度不代表變更已執行或保證稍後執行安全。前置觀察若完整證實違反停止門檻（如複製延遲 45s > 5s 預算、高負載超標等），依充分證據優先序判 `not-met`，同時停止執行交接；當前置條件、操作適用性、復原方案、風險接受、防鎖出、客戶端信任配合或有效批准未滿足，或前置觀察因負載／時間預算截斷而未能完成時，等待人工解除、補齊前置觀察或批准前為 `blocked`；若屬自管平台層越界或前置觀察存在未解決矛盾／缺基準無法判定，依四態規則判 `indeterminate`。已批准且前置齊全、等待人工執行時，技術就緒與等待執行分開陳述，依本次選定定義回報（若主張定義為「變更執行完成」則等待人工執行為 `blocked`；若定義為「執行前準備就緒且可交接人工執行」則全部前置與有效批准齊備時可為 `met`，但必須明示尚未執行）。 |
| 指定變更的實際變更與物件有效性符合預期（`post_change_effect`） | 執行後的計畫／事件識別、實際目標與操作、執行紀錄，以及按變更類型固定的核心效果：DDL 為實際 schema 差異與物件／約束／索引有效性（含確認無 `INVALID` 索引或部分提交缺漏）；權限變更為預期授予與撤銷在目標帳號／角色上的實際生效狀態；TLS／憑證變更為伺服器／平台生效設定與憑證狀態。命令回傳成功或表存在不等於此項符合；部分完成、產生 `INVALID` 索引或實際狀態不符為 `not-met`；若操作仍在執行中且遇批准撤回／等待人工安全停止與狀態重查則為 `blocked`；執行結果未知或未重查為 `indeterminate`。 |
| 指定變更的資料與不變條件驗證符合基準（`post_change_data`） | 資料／應用負責人確認的資料完整性、約束或業務不變條件基準與執行後實際驗證結果。違反基準為 `not-met`；缺基準或未完成驗證為 `indeterminate`。 |
| 指定變更的應用與存取驗證符合要求（`post_change_access_app`） | 依變更類型固定的存取與應用驗證：DDL 為應用相容性與服務正常；權限變更為必要的允許／拒絕存取探測、應用存取與管理者／驗證者未被鎖出，並按版本與帳號核對既有連線與新連線的生效差異；TLS／憑證變更為指定客戶端信任／主機名驗證、新連線／重連成功、必要的非合規連線拒絕，以及應用可用性。不能由舊連線仍正常、單一 GRANT 成功或資料庫設定成功推導此項符合。存取／重連失敗、仍接受禁用連線或管理／應用中斷為 `not-met`；缺人工探測或應用證據為 `indeterminate`。 |
| 指定變更後的負載、複製健康與無殘留符合要求（`post_change_health_cleanup`） | 變更後的負載與複製健康符合門檻，且無未處理的殘留臨時表、`INVALID` 索引、舊權限／過渡物件或未完成清理。存在 `INVALID` 索引、殘留物件、清理／復原失敗或負載／複製超標按該子主張定義判 `not-met`（若清理／復原僅作為收尾事項且未併入此主張定義，則保留已成立的技術主張結論，並在交接與收尾狀態明示未收尾與殘留）。 |

若使用者將變更前準備拆為更細的必要主張（例如適用性、預算與前置環境、復原準備、批准交接），或將執行後驗證拆為 schema／物件、權限效果、存取探測、客戶端重連、資料、應用、複製健康、殘留清理等獨立 ID，必須逐一按上列最低證據分項判定，不合併掩蓋。

## 4．變更前準備、預算、復原與外部工具邊界

準備任何 B3 變更（DDL、權限、TLS）的人工執行交接（runbook）時，輸出必須逐項明列：

1. **目標、計畫版本、引擎完整版本、適用的儲存引擎、操作適用性、具體操作順序、預期差異、受影響依賴、影響範圍、人工執行者與各責任人**。
2. **交易邊界、implicit commit、鎖取得／持有風險、演算法限制（如 `ALGORITHM`／`LOCK`）、資料重寫、額外空間與複製影響**。不得以 `online`、`concurrent`、`instant` 名稱直接推導無鎖、無重寫或無影響。
3. **經變更負責人確認的鎖等待預算、操作與影響時間預算、查詢負載／容量門檻、複製健康門檻、觀察方式、安全停止門檻與方式，以及誰執行停止**。各項預算獨立；**dbcli 或 SQL 查詢逾時絕不冒充 DDL 的伺服器端鎖等待控制**。
4. **前置證據的取得時間、時效，以及人工接手執行前必須重新核查的條件**（目前長交易／blocker、活躍連線、高負載、可用空間、複製延遲、版本與目標身分）。舊快照不能掩蓋執行當下的長交易、高負載、空間不足或來源矛盾；歷史變更執行時間落在批准有效時間窗內即屬時序一致，不宣稱不存在的批准時間矛盾，受控包內嵌原始紀錄與來源即可作為合格依據，不額外要求獨立外部原件。
5. **可行復原方案、適用前提、預估影響、復原負責人、批准範圍、執行後必要驗證項目（含負責執行探測的人員與預算）及殘留處置**。

### 關鍵停止與禁止行為

- **長交易／鎖等待、高負載、空間不足或複製超標**：前置觀察發現超標時，立即停止受影響變更的執行交接（未開始者記為不可執行／`blocked`）；已開始的操作交由指定人員依安全停止計畫處理。**嚴禁自動 `KILL`／終止其他連線、自動延長鎖等待或時間預算、或調低安全門檻**。
- **版本／操作不適用、演算法／鎖要求不滿足或需外部 OSC**：當目標引擎版本、儲存引擎或表結構不支援所要求的 `ALGORITHM`／`LOCK`（例如要求 `INSTANT`／`INPLACE`、`LOCK=NONE` 但實際需 table rebuild 或排他鎖），或操作規模／特性需要 `gh-ost`、`pt-online-schema-change` 等外部工具時，**不得靜默降級演算法或鎖等級、不得自動替換為外部工具執行，也不提供完整外部 OSC 操作流程**；必須記錄不適用原因、限制與待補條件，停止就緒宣告並交由變更負責人／專家重新規劃與批准。
- **DDL 失敗、逾時或連線中斷**：失敗、逾時或斷線不代表伺服器端未產生變更或已整批回滾。必須先以唯讀觀察重查實際 schema、物件有效性（如 PG `pg_index.indisvalid`）與各步提交狀態，區分未提交交易回滾、implicit commit、MySQL temporary table 不可回滾與多步操作部分完成；**未確認實際狀態並取得涵蓋重試／清理的批准前，嚴禁盲目重跑**。
- **復原與不可逆風險**：只有「備份存在」不足以證明可復原本次變更；若以備份／PITR 作為復原方案，須引用 B1 合格且對本次目標與時間窗適用的復原證據（不強制重演，但須指出整庫／時間點還原對變更後新寫入的影響）。若操作確實無通用 rollback 且無法補償復原，必須由有權者明確接受該計畫的不可復原風險並確認停止／善後方式；**若專案政策有強制復原要求，任何人均不得以風險接受豁免該強制要求**。缺少合格復原方案或有效風險接受時，runbook 保留待補條件，不得標為已具備執行條件。
- **權限與 TLS 變更特殊要求**：權限變更交接必須確認受影響帳號、應用與管理存取、既有連線與新連線的生效條件（例如角色啟用、快取或需重連），以及避免管理者與驗證者被鎖出的具體步驟；**agent 不得建立備援帳號或持續存取**。TLS／憑證變更交接必須確認指定客戶端信任 CA 部署順序、主機名驗證相容性、伺服器生效／重啟條件與重連驗證計畫；資料庫端設定成功不替代客戶端可用性。

## 5．批准、執行交接、執行後驗證與收尾

沿用 ADR-0047：批准綁定確切計畫版本、環境、資源、操作、本次時間窗與允許重試次數，並核對批准者資格與可追溯來源。批准點設於人工變更、額外身分／寫入探測、復原與清理前。單一有效批准可明確涵蓋多個步驟（例如變更＋驗證探測＋清理），無須重複索取同一授權；每步仍核對目標、前置條件與批准適用性。

批准拒絕、過期、撤回、資格未確認、計畫版本或條件實質改變、或超出允許重試次數時，停止未開始的相關交接；**已開始的操作遇批准撤回或超界時，交由人工執行者依安全停止計畫處理，不宣稱自動取消或已回滾（撤回不等於回滾）**。批准、dbcli gate 與技術判定互不替代；操作成功但沒有批准證據，不能事後補稱已獲准。

執行後交回計畫／事件識別、實際目標與操作、成功／失敗／部分完成／狀態未知紀錄、起訖及等待時間、停止／重試、前後觀察、各必要驗證結果與殘留情況。任何可能寫入、使用額外身分（如以受測帳號測試允許／拒絕）、改變連線政策或造成負載的探測，**必須事先明列在批准計畫並由指定人工執行者執行後交回證據；agent 嚴禁自行切換未授權身分或試做寫入以證明拒絕**。

### 清理與復原執行交接（四項前置核對）

準備人工清理（例如清理 PG `INVALID` 索引、移除臨時物件或撤銷測試授權）或人工復原的執行交接時，**包括在 `post_change_*` 驗證失敗／部分完成後提出任何補償復原、退回舊設定／憑證、修正客戶端配置，或在 `handoffs` 中宣稱指定條件（如重獲批准）成立後即可由人工開始清理／復原的交接**，輸出必須逐項明列這四項前置核對（由本次指定的人工執行者與證據保管／交回責任人負責）：**清理／復原目標、明確操作／刪除範圍、必要證據已成功保存且可取得、當步批准仍有效且涵蓋該範圍（含重試次數，上限為 0，不得擅自重試）**。四項成立後才交人執行；有缺項便標為等待核對，列接手人及解除條件。目標核對必須按已讀取證據與連線設定（優先沿用 `config.json` 中明載之 `connections.<name>.database`，如 `fixture`）明確列出具體資源與資料庫名稱，不得將已提供的資料庫名稱錯報為缺失或待人工補齊；不能只寫「依原批准清理／復原」或「前置核對完成後執行」而省略具體核對欄位。當 `post_change_*` 驗證失敗／部分完成（例如既有連線仍持有舊權限、或需要連線池回收／補償操作）而交付後續修正或探測時，亦須維持等待核對／未就緒狀態，並逐項核對上述四項條件，切勿以「依經確認有效的批准計畫由人工完成」等概括交付代替前提核對；若僅為規劃交接，應明確宣告「僅為規劃／停止交接，不授權或交付操作執行」。僅通知批准拒絕／過期／撤回／計畫變更或停止未開始操作（且不附帶「重獲批准後執行清理／復原」之條件式執行交接），不等於清理執行交接。

清理或復原失敗時，必須明示**未收尾、殘留物件／權限／設定狀態、失敗原因、接手人及解除條件**；若再次清理／復原屬重試且原批准額度已用盡，先交批准者重新授權，不直接交接再次執行。未收尾不覆寫已成立的歷史技術結論。

## 6．歷史適用性與交付聲明

可評估可追溯的歷史稽核或歷史變更事件，不強制重演。當評估範圍選定為指定歷史變更事件時，`post_change_*` 主張依該次歷史事件當時的有效驗證證據判定（只要當次驗證在事件當時有效，不因距離後續參考時間超過即時觀察時效而將已成立的歷史事件結論改判 `indeterminate`）；結論明確限定當次引擎版本、儲存引擎、操作、基準、身分、環境與驗證條件，並另列目前政策、帳號／角色、schema、憑證、客戶端／驅動或部署變動造成的目前適用性缺口。新的評估不覆寫舊結論；歷史成功不自動升格為目前符合，歷史變更若當時缺少有效人工批准，必須保留批准合規缺口，不因技術結果成功而偽造或補認當時批准。

當歷史目標或原始證據已不可取得，先由證據責任人確認是否有當次合格受控替代；無合格替代時，相關主張為 `indeterminate`。

依共用結果格式逐項引用證據、檔案完整 SHA-256 與混合狀態，列出每項缺口的受影響範圍、已有證據、缺項、原因、解除條件與接手人。

F 是真正 Skill 的合成行為測試：正確判出 `not-met`、`blocked` 或 `indeterminate` 可使行為測試 PASS，但**不能證明資料庫主張 `met`，也不能抵銷 L／R 實環境缺口**。完整 B3 另需三引擎隔離自管 L（受限帳號權限稽核與人工授予／撤銷前後正反例、指定客戶端 TLS 正反例、正常原生 DDL 完整變更鏈、PG concurrent index `INVALID` 殘留與清理、MySQL／MariaDB 各自多步操作部分完成、三引擎受控鎖等待／長交易）與三引擎真實 RDS R（受限帳號正常取證／安全無權／受管角色限制、設定 pending→生效完整鏈、憑證更新成功與指定客戶端重連／驗證及應用可用性證據）及同候選人類審查。僅 F 全部通過可稱「B3 行為驗收通過，實環境驗收未完成」，未驗部分逐項保留；不代表安裝或發布批准。
