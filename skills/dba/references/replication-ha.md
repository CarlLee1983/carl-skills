# B2：Replication／HA 評估與人工交接

遇到角色／拓樸、replication 健康、HA 設定或指定切換演練／事件評估時使用本流程。先遵守 [共用能力、結果與證據規則](../SKILL.md)。完成條件是：固定範圍的每個必要主張都有判定、可追溯理由與缺口／接手人；全部必要主張 met 才稱本次範圍全部符合。複製健康與事件驗證是子主張摘要，不增設單一成功狀態。

## 1．固定評估契約

開始時選定一項或多項：角色／拓樸、指定時間窗內複製健康、HA 設定、指定演練／事件驗證。記錄資源／節點身分、環境、引擎完整版本、部署、複製模式／通道、預期關係、參考時間／時區、觀察起訖與新觀察或歷史證據。多節點／通道列完整範圍，事先固定必要子主張、最低證據與不適用理由；未知不是不適用，未選項仍「本次未評估」。

由資料／服務負責人確認 lag 門檻、取樣間隔／覆蓋、時效、負載／逾時預算、RPO／RTO、量測起訖與服務恢復標準；資料／應用負責人確認關鍵資料、業務不變條件及事件截點基準。指定有權批准者、人工執行者、流量／寫入負責人及證據交回人。可提出建議，但沒有確認的數字不當作政策。缺基準保留可讀觀察，僅無法判定的主張為 indeterminate。

引擎層涵蓋 PostgreSQL、MySQL、MariaDB 的自管與 AWS RDS；平台層僅 RDS，不含 Aurora。自管或其他平台未涵蓋的主張為 indeterminate，交人處理；自管平台切換／故障管理 runbook 不在範圍。正式 RDS 可準備人工 runbook，不承擔即時事故指揮。新演練使用隔離環境，所有建立、設定、故障注入、切換、流量調整、回切／重建及清除皆由人執行。

## 2．有限觀察與來源語意

以共用 requirement set 檢查 capability／contract 後，僅做已選計畫內的唯讀觀察。每輪有起訖、間隔、樣本覆蓋、查詢負載與逾時預算，不建立持續監控或存取。樣本綁定取得時間、訊號時間、節點／來源／通道、單位與語意。停止時保留原窗與缺樣，不延長或縮小窗口湊通過；逾時不等於伺服器已取消查詢。身分不明停止該目標查詢；其他安全且獨立評估可繼續，contract 版本不支援仍停止整個流程。

| 引擎／來源 | 判讀時必須保留的邊界 |
| --- | --- |
| PostgreSQL | 依版本及模式確認 recovery 狀態、sender／receiver／上下游、接收／套用 LSN、slot／WAL。LSN 差是同一來源與時間範圍的位元組差，不是業務 RPO；統計 lag、最後 replay 時間與無寫入期不可混為同一延遲定義。 |
| MySQL | 版本適用的 replica／source status、performance_schema、server／channel、GTID、IO／applier 進度與錯誤。保留各通道，單次 Seconds_Behind_Source=0 不證明完整時間窗健康；NULL 或缺列先按來源／執行狀態解讀。 |
| MariaDB | 使用自身版本的單／多來源 replica status、Connection_name、binlog 與 GTID domain 語意；不得套用 MySQL GTID 函式或把 domain／channel 混算。停止與另一條通道前進分開保留。 |
| RDS | 對應同一資源的部署／成員／AZ／角色、端點、事件與窗口內指標。Multi-AZ DB instance standby SQL 不可見不表示沒有 HA；平台設定只支持設定主張，不補足健康或切換證據。 |

先核對實際版本與來源語意，再選計畫內 SQL；涉及表／視圖先 `blacklist list --format json` 與 `schema <qualified-object> --format json`，SHOW／純函式不虛構 schema。不同節點、通道、時刻或統計快取／快照不能直接視為同時快照；必須有已確認的對齊方式或區間界限。同源兩個指標不是兩份獨立佐證。無寫入期無進度可以合理，但需來源證據及政策，不把 NULL／哨兵值機械地當健康或故障。無權、查詢失敗、blacklist／LIMIT 省略不是節點不存在。

## 3．分項最低證據

以下名稱可對應本次固定的 claim ID。使用者已給 ID 與定義時保留其對應，不移除不利子主張。結果 claims 只列事先固定的必要子主張；不改寫 ID 或額外新增判定。未選的資料／應用／RPO／RTO、操作合規與收尾事項可在未評估、缺口或交接說明。若事先選的是整體事件驗證，開始時先固定其必要子主張；若只選角色／端點轉換，則維持該範圍。充分且無相關矛盾先判 met／not-met；相關矛盾優先於阻礙，為 indeterminate；其餘依共用四態規則。已有充分違反證據不因另一輔助觀察受阻或缺樣改成未知。

| 主張 | 最低證據與分項界線 |
| --- | --- |
| 角色／拓樸 | 預期拓樸、身分與時間、實際角色及來源／接收關係；SQL 與平台對應同一對象。read-only 或可連線不能推出全拓樸。部分節點／通道可見不代表完整。 |
| lag | 已確認門檻、指定窗的合格樣本與來源語意。充分超標為 not-met；單次 0、過時、缺樣或缺政策不足以稱整窗符合。 |
| 複製運作／進度 | 適用通道接收／套用運作與來源／接收／套用進度；活躍寫入與無寫入分開（只依 `replication` 與已確認的 `idleProgressRule` 判讀；未選 `retention` 主張時，不跨欄位把未同步修訂的背景 `retention.slotOrChannelPositions` 當成與 `replication` 無寫入樣本的矛盾）。充分停止／不前進證據按政策為 not-met，不能由其他通道前進抵銷。 |
| 複製錯誤 | 指定窗的適用錯誤與運作證據，按政策判定；查詢本身失敗不自動等於 replication 錯誤。 |
| WAL／binlog 保留風險 | 適用設定、slot／通道位置或日誌用量、必要容量／時間序列與風險界限。充分超標 not-met；必要資料不足 indeterminate，不由低 lag 或瞬間用量宣稱安全／預測耗盡時間。 |
| HA 設定 | 同一資源適用部署、成員／AZ／角色、時間與配置要求。設定符合不證明 standby 即時健康或切換能力。 |
| 事件角色／端點轉換 | 指定事件與操作／平台紀錄、前後身分／角色／端點、時間與一致對象鏈；平台完成不能代替資料與應用證據。 |
| 資料驗證 | 與事件截點相容的關鍵資料／業務基準與實際驗證。通用筆數、摘要或可連線不自動充分；需要寫入的探測由人按計畫執行。 |
| RPO | 已確認目標、參考時間、可證實復原點／遺失範圍或足夠界限、基準與計算依據。lag／LSN／GTID 不能冒充業務資料損失。區間跨越門檻為 indeterminate；獨立且合格的復原點證據可單獨判定，不因其他資料不變條件失敗一律抹去。 |
| 應用恢復 | 應用負責人確認的服務基準與實際結果、端點／連線對象。仍連舊端點或充分服務失敗為 not-met；沒有應用證據為 indeterminate。 |
| RTO | 政策定義的相容起訖與應用恢復證據，與應用恢復分項。保存平台耗時（`startedAt` 至 `platformFinishedAt`）、事件宣告至開始操作的等待時間（`incidentAt` 至 `startedAt`）、應用恢復、必要驗證總耗時及等待（勿將 `incidentAt` 至 `platformFinishedAt` 的含等待合計誤稱為平台操作耗時）。明確未在期限內恢復可 not-met；沒有合格起訖或應用證據不能用平台耗時替代，也不能刪等待。 |
| 保護恢復 | 新拓樸、必要複製／HA 設定及切換後指定健康窗。提升 primary 或服務恢復不表示保護已重建；以前未恢復及後來恢復分別記錄，不覆寫。 |

CALL 拒絕取得不到的觀察為 indeterminate，交既有授權人員取證，不升權／自動換 AWS 或原生客戶端；原計畫內獨立 RDS 唯讀觀察可繼續。缺 AWS CLI／唯讀 IAM、原生無權或查詢失敗按證據缺口判讀，不自動建立新 dbcli Tool 缺口。必要證據保存失敗且無可取得合格替代時，相關主張 indeterminate；有合格受控替代則保留有效結論並揭露保存失敗。

## 4．操作別 runbook 與人工批准

先辨識操作適用性，再準備人工交接；未滿足必要條件的 runbook 保留缺口但不可標「可執行」。

| 操作 | 交接差異 |
| --- | --- |
| RDS Multi-AZ DB instance 切換 | 核對 instance 部署、適用平台操作、端點／DNS 與重新連線、寫入／流量責任。standby 不可見時不要求虛構 SQL 追平證據，平台負責事項與人工確認事項分列。 |
| RDS Multi-AZ DB cluster 切換 | 核對 cluster、成員／writer 及支援的引擎／版本／區域；不把 instance 操作或 Aurora 命令套上。固定目標、角色／端點與驗證計畫。 |
| Read replica promotion | 核對實際 replica 關係與適用狀態；計畫內 promotion 的來源停寫、追平、流量轉移與雙寫防護由指定人確認。promotion 後是獨立 instance，後續保護／重建另列；無通用一鍵撤銷。 |
| 回切／重建／清除 | 各自列目標、範圍、前置證據與有效批准；不能當作原切換的自動回滾。涉及清除時，使用下列「收尾交接」的完整前置核對；失敗明示殘留、原因、接手人及下一步。 |

不要把 promotion 的 SQL 追平條件套成每種 Multi-AZ 的共同門檻。原 primary 已故障或 standby 不可見，不編造證據或把未知說成無資料損失。平台建議、平台硬限制及專案另定政策分開；備份完成不是所有 B2 操作的通用平台前置條件。

交接內容須包含：目標與計畫版本、適用性與前置證據、隔離／避免正式流量與外連／存取限制、批准者資格、人工執行者、流量／寫入控制及避免雙寫的責任與證據、預期影響／資料損失／停機／費用、停止方式、不可逆性／回復限制、時間窗、重試範圍與驗證計畫。缺寫入控制或隔離不宣稱安全切換就緒。

人工建立／變更／注入／切換／回切重建／清除前核對批准。單一有效批准明確涵蓋多步時沿用，不重複索取相同授權；仍逐步確認目標、條件與時效。拒絕、過期、撤回、資格未明、範圍／計畫實質變更或超範圍重試，停止未開始的相關交接；已開始操作由人依安全停止計畫處理，不稱自動取消／回滾。等待批准與等待人工執行分別記原因、解除條件及接手人。批准、dbcli gate 與技術判定互不替代。

交回人工操作、平台事件、前後身分／拓樸／端點、時間、資料／應用驗證、RPO／RTO、保護恢復與收尾紀錄。自動平台事件事後評估不偽造事前人工批准；人工操作缺批准不能因成功補稱合規，技術結論與合規分開。

### 收尾交接

準備人工清除的執行交接時，**包括在 `handoffs` 中把「清除」與切換／重建一併列為待重新取得批准後即可由人工執行的條件式交接**，輸出必須明列這四項前置核對（由本次指定的人工執行者與證據保管／交回責任人負責）：**清除目標、明確刪除範圍、必要證據已成功保存且可取得、當步批准仍有效且涵蓋該範圍**。四項成立後才交人開始清除；有缺項便標為等待核對，列接手人及解除條件。不能只寫「依原批准收尾」或一般性的「批准有效且當步前置條件核對完成後執行計畫內操作」而省略具體四項欄位。這是將來人工動作的執行前檢查，不代表 Skill 已保存證據或已清除資源，也不要求重複取得仍有效的批准。

僅通知批准拒絕／過期／撤回／計畫變更、停止尚未開始的操作，或列出受阻操作名稱（此時不附加「待重獲批准後由人工執行清除」的交接語句），不代表清除執行交接或已具執行條件。當因批准變更／拒絕／過期而停止操作時，交接應明確限於停止通知與重新審核要求，**嚴禁概括交代「取得現行計畫的有效批准並逐步確認前置條件後由人工操作」，亦不可將包含 cleanup 在內的操作交付執行**；若交接涉及 cleanup，必須逐項明列上述四項前置核對（清除目標、明確刪除範圍、必要證據已保存且可取得、當步批准仍有效且涵蓋該範圍），在條件齊備前維持受阻／未就緒，不交付清除執行。後續若準備清除執行，仍須完成上述四項核對；有效批准不能單獨代表就緒。

## 5．歷史適用性與交付

可評估可追溯歷史演練或正式事件，不強制重演。結論限定該次環境、版本、拓樸、通道、設定、操作與驗證條件；目前版本／端點／節點／應用基準改變另列適用性缺口，不把歷史成功變成目前能力。重新評估產生新紀錄，不覆寫舊結論。

依共用結果格式逐項引用證據、雜湊與混合狀態，列缺項、原因、解除條件、接手人及下一動作。操作完成但清除／重建失敗要說未收尾，不抹去已成立歷史切換結論。所有必要主張 met 只支持本次固定範圍。

F 是真正 Skill 的合成行為測試，正確 not-met／blocked／indeterminate 可使行為 PASS，但不是資料庫主張 met。完整 B2 另需三引擎隔離 primary＋replica（MySQL／MariaDB 真實雙通道）、八條 RDS 操作路徑與每條保護恢復正向證據、受限帳號及版本／TLS／應用等實證和同候選人類審查。僅 F 全部通過可稱「B2 行為驗收通過，實環境驗收未完成」，未驗部分逐項保留；不代表安裝或發布批准。
