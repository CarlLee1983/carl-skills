# Optional Impeccable collaboration

Read when considering installed Impeccable for review or scoped refinement. Keep its upstream installation separate from this skill; use its current instructions as the authority for command names, prerequisites and execution. Its absence leaves this flow usable through the [capability selection rules](collaboration.md#choose-among-candidates).

## Match the command to the question

Choose a command for this round's unresolved question, not merely because Impeccable is installed:

| Question | Candidate commands | Boundary |
| --- | --- | --- |
| What implementation defects affect accessibility, responsive behavior or technical quality? | `audit` | Assess the named prototype, screen or component; findings are proposals for fixes. |
| What hurts hierarchy, clarity or the representative task? | `critique` | Use when a fuller design assessment warrants its required evidence and orchestration. |
| Which known detail needs improvement? | `clarify`, `typeset`, `layout`, `harden`, `polish` | Match the diagnosed problem and authorized refinement scope; preserve accepted structure, content and visual rules outside it. |

Keep task discovery, direction comparison and finalization in design-experience. Impeccable's `init`, `shape`, full new-work and live setup are outside this default handoff; consider them only when the requested deliverable calls for that workflow and it passes the same compatibility checks. Selecting a review or refinement command does not select its whole design workflow.

## Check compatibility before activation

Read the installed entry point and selected command's references before invoking its launcher or initialization. Check its required assessment scope, context-loading directives, tools and agents, evidence, closing questions and artifact destinations against this round. A comprehensive `audit` may exceed a request limited to keyboard and mobile checks; choose a fitting method rather than expanding the assessment or presenting a partial run as the full command. In particular, web `critique` can require independent design and detector/browser assessments plus persisted reports; check the native procedure separately. Treat these as a command's process, not a lightweight checklist.

Pass the accepted brief, current SESSION decisions, target/version, question, allowed changes and artifact boundary. Apply the [flow ownership rules](collaboration.md#keep-this-flow-in-charge) to any required product-context files: derive them from SESSION rather than repeating settled discovery. Resolve initialization that would exceed the grant before activating the command.

Distinguish an overridable default from an absolute rule in the installed version. A brand's accepted heading labels, for example, can conflict with a non-overridable eyebrow ban. Resolve such a conflict through [candidate selection and preference](collaboration.md#choose-among-candidates); do not silently change the brief or skip a required procedure while claiming Impeccable compliance.

Use the existing [tool write boundary](collaboration.md#bound-tool-writes-before-delegating) for context files, reports and `.impeccable` state before execution. Installation, updates, hooks and unrelated configuration are separate actions requiring their own authorization.

## Return results to the design flow

Link any command report and evidence from SESSION using the [evidence record](artifacts.md#evidence-bound-self-review). Keep detector findings, expert judgments and user feedback distinguishable; scores cover only the evaluation actually run. Continue at the current design stage with the findings or scoped changes, retaining the [taste baseline](taste-baseline.md) and existing finalization criteria.
