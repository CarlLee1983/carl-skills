# humanize-writing 驗收案例

修改 humanize-writing 的規則後，用本文件重放案例。驗收看的是行為：成稿該留的有沒有留、該改的有沒有改，以及腳本的命令列輸出。規則分在哪個檔、措辭怎麼寫，都不在驗收範圍內。格式與連結檢查不能代替重放。

安裝只需完整的 `skills/humanize-writing/`；本文件、`fixtures/` 與 `.scratch/` 都不是執行依賴。

規格與工單：[`.scratch/humanize-writing-merge/`](../../.scratch/humanize-writing-merge/spec.md)。每個案例的「工單」欄填的是該目錄 `issues/` 的編號，表示這條行為是由哪張工單引入或修正的。

## 重放方法

1. **改稿（盲測）**：開一個新的子代理，只給它來源目錄 `skills/humanize-writing/` 的路徑，以及 `fixtures/` 底下 `h` 開頭的輸入稿，並告訴它只能讀這兩處。它看不到本文件，也看不到 `s` 開頭的腳本測試稿。要求它：
   - 先讀 `SKILL.md`，再照 `SKILL.md` 的指示讀對應的 references，然後逐篇潤飾。
   - 不呼叫 Skill 工具，也不讀其他位置的 humanize-writing 副本，例如 `~/.claude/skills/`、`~/.codex/skills/`、`~/.agents/skills/`。
   - 每篇的回覆格式都照技能本身的交付規則。H14 用來檢查交付格式，所以不另外規定輸出格式。
   - 輸入稿第一行若有 HTML 註解標明「介面文案」，就當作介面文案處理。
2. **判定**：另開一個子代理，給它本文件、輸入稿和改稿成稿，讓它逐案判「通過／不通過／部分」，每項附上成稿裡的證據句。判準以重放當下的本文件為準。判定之後如果修改了判準，要重新派判定子代理判一次，不能由派工的代理自己改判。
3. **紀錄**：寫到 `.scratch/humanize-writing/validation/`。每次重放產生兩個檔，`acceptance-<標記>-drafts.md` 放成稿，`acceptance-<標記>.md` 放判定。兩個檔都要寫明重放時來源目錄的 commit。
4. **觸發案例**（T 系列）：不經過改稿子代理。由判定子代理只讀 `SKILL.md` 的 frontmatter description 來判。
5. **來源目錄自查**（H10）和**腳本案例**（S 系列）：直接在終端執行，比對輸出與退出碼。

判定原則：「預期保留」有任何一項沒做到，就是不通過；「預期改寫」大部分做到但有遺漏，判「部分」。

## 改稿案例

### H01 破折號

- **輸入**：`fixtures/h01-dash.md`
- **預期改寫**：成稿不出現 `—`、`——`，改用逗號、句號或括號。
- **預期保留**：40ms、900ms、「舊索引沒有重建」、「第一個小時」、「幾乎每個列表頁」。
- **工單**：02

### H02 提示性冒號與放行的冒號

- **輸入**：`fixtures/h02-colon.md`
- **預期改寫**：「重點只有一個：別讓…」和「教訓是：監控比預案更重要」這兩處，不再用冒號先鋪梗、再揭曉重點。
- **預期保留**：
  - 這幾處冒號：「原因有兩個：」（後面接條列）、「時間：14:00」、「注意：灰度期間…」
  - 小標「快取失效」
  - 兩個條列項的內容
- **工單**：02

### H03 排比

- **輸入**：`fixtures/h03-parallel.md`
- **預期保留**：四件具體改動全部保留，不能被砍成兩項：佇列、重試上限 10→3、逾時、DLQ。
- **預期改寫**：「更優雅」「更面向未來」這類沒有內容支撐的項目不出現在成稿。有前文改動支撐的評價可以留，例如穩定、快，項數不限。
- **工單**：02

### H04 文章小標要講內容

- **輸入**：`fixtures/h04-heading.md`
- **預期改寫**：空泛的小標「一些想法」改成能講出本節內容的標題。
- **預期保留**：offset、cursor、keyset、「第 1,000 頁」。
- **工單**：現行規則

### H05 「不只…更」

- **輸入**：`fixtures/h05-buzhi.md`
- **預期保留**：第一句是單純的遞進，「不只…更」的句式和兩項影響都要留下。
- **預期改寫**：第二句「這不只是硬體問題，更是架構問題」放在翻案位置，要改成直述。換成「除了…也」之類意思相同的翻案句式，仍算不通過。
- **工單**：02

### H06 疊加保留語氣

- **輸入**：`fixtures/h06-hedge.md`
- **預期改寫**：「可能」「或許」「在某種程度上」只留一層。
- **預期保留**：
  - 整句仍是不確定的語氣，不能變成斷言（例如「會讓冷啟動變慢」），也不能變得更弱。
  - 「稍微」「冷啟動」。
- **工單**：02

### H07 受保護片段

- **輸入**：`fixtures/h07-protected.md`
- **預期保留**：下列片段逐字不變，用 diff 比對。
  - AI 使用聲明、合作推廣聲明、免責聲明三句
  - 程式碼區塊
  - 路徑 `/etc/app/config.yaml`
  - 網址 `https://example.com/docs/rollout?ref=v2`
  - 引號裡同事的原話，包括其中的破折號
- **預期改寫**：最後一句空泛的收尾要刪掉，或改得具體，但不能編出原文沒有的事實。
- **工單**：07

### H08 介面文案套用介面規則

- **輸入**：`fixtures/h08-ui-copy.md`（第一行的註解標明是介面文案）
- **預期改寫**：
  - 按鈕「了解更多」改成講出具體動作的文字。
  - 「更好、更快、更安全」改成能查證的好處，或刪掉。
- **允許、但不要求**：首頁標題可以留著現在的摘要格式，也可以改成招牌式的口號；兩種寫法都算通過。
- **預期保留**：HTML 標籤結構、產品名 Orbit。
- **工單**：05

### H08b 文章小標不套用介面規則

- **輸入**：`fixtures/h08b-article-heading.md`
- **預期改寫**：小標「讓「做完了」這句話變貴」是口號，放在文章裡要改成講內容的標題，例如寫出定義完成的三項證據。
- **預期保留**：三項條件：PR 合併、部署成功、監控十分鐘沒有錯誤。
- **工單**：05。「文章小標要講內容」是現行規則，但現行規則沒有涵蓋口號式的小標；05 要在劃清介面文案範圍的同時補上這一點。

### H09 敘事模式不受誤傷

- **輸入**：`fixtures/h09-narrative.md`
- **預期保留**：
  - 刻意的重複：「我按掉，它又響。我再按掉，它還是響。」
  - 「凌晨三點」
  - 小陳的對白
  - 結尾停在內心獨白
  - 第一人稱口吻
  - 結尾「心想：」的冒號，後面接的是心裡的原話，屬於放行的冒號
- **預期改寫**：沒有必須改的地方。成稿沒有加上總結句、也沒有砍掉重複，就算通過。
- **工單**：現行規則，每張工單完成後都要重跑。

### H10 來源目錄自身行文（終端自查）

- **做法**：在來源目錄所有 `.md` 檔中搜尋 `—`，逐筆檢查命中的位置。
- **預期**：
  - 命中只出現在下列兩種位置：被標示為反例的段落（例如 ❌ 句、引號內的原句）、說明破折號規則本身的段落。
  - 規則說明的行文中沒有破折號。
  - 用來示範「破折號被禁」的反例仍然保留在規則檔裡。
- **工單**：02

### H11 英文新併入規則

- **輸入**：`fixtures/h11-en-new-rules.md`
- **預期改寫**：
  - 宣傳腔（"Nestled at the heart"）
  - 意義膨脹（"serves as a testament"）：不能換一種說法，改寫成「這顯示了我們多重視…」的主張，例如 "shows how seriously we take"。
  - 模糊歸因（"Experts argue"）
  - 挑戰與展望段（"Despite facing challenges… continues to thrive"）
  - emoji 與粗體標題清單
  - 聊天殘留（"I hope this helps!…"）
- **預期保留**：scheduler、"fast"、"simple" 這些具體描述，可以合併成一般句子。
- **工單**：04

### H12 中文新併入規則

- **輸入**：`fixtures/h12-zh-new-rules.md`
- **預期改寫**：
  - 挑戰與展望段
  - 動詞名詞化（「進行了全面的優化」）
  - 商業黑話（「打通…閉環」「賦能」）：不能換個說法留下，例如「把資料閉環接起來」仍算黑話。
  - 意義膨脹（「標誌著」「彰顯了」）
  - 聊天殘留（「希望這篇文章對你有幫助！」）
- **預期保留**：不能編造原文沒有的成果或數字；原文沒有細節時，寧可把句子刪掉。成稿只剩空殼時，句子應該刪掉，而不是被潤飾成通順的空話。這一點也驗證「先處理結構、再處理用字」。
- **工單**：03

### H13 現行規則（基準）

- **輸入**：`fixtures/h13-existing.md`
- **預期改寫**：
  - 「不是…而是」二元對比殼：可以保留對比的兩件事實，但不能用「不是…而是」或換字的變形。直接陳述判斷就可以，例如「問題出在設計，不在效能」。
  - 「本文未在讀者環境驗證」：改成第一人稱，或省略主詞。
  - 對岸用語：用戶→使用者、異步→非同步、隊列→佇列、數據→資料。
- **預期保留**：效能和設計這兩個判斷、「高峰期會堆積」這項事實、未驗證的範圍限定。
- **工單**：現行規則

### H14 交付格式

- **輸入**：`fixtures/h14-delivery.md`
- **預期**：
  - 回覆先給完整成稿。
  - 修改清單只在必要時才附，而且放在成稿之後。
  - 成稿保留 7→30 天、10→30 秒兩組數字。
  - 開頭的時代背景、結尾的空泛總結都刪掉。
- **工單**：07

## 觸發案例

只讀 `SKILL.md` 的 description。每個請求代表一個獨立的觸發情境，description 裡要有對應這個情境的觸發詞或明確描述，才算通過；只靠「去 AI 味」之類的泛稱推得出來，不算。三項都通過，T 系列才算通過。T02 在合併前就已經通過，保留它是為了防止日後退步。

- **T01**：「幫我把這段改得像本人寫的。」
- **T02**："Can you edit this X post so it sounds less robotic?"
- **T03**："This draft feels over-polished. Fix it."
- **工單**：07
