# design-experience 維護驗收

本文件供修改技能後選擇受影響的驗收情境；安裝只需完整的 `skills/design-experience/`。流程以 [SKILL.md](../../skills/design-experience/SKILL.md) 為準。

## 封裝與安裝

1. 將單一技能目錄複製到暫存目錄，確認 `SKILL.md`、其引用的 `references/`、`agents/openai.yaml` 與 `LICENSE` 齊全。
2. 對暫存副本執行 README 的 `quick_validate.py` 命令。此可選維護工具需要 Python 與 PyYAML，不是技能執行依賴。
3. 檢查 Markdown 的必要本機相對連結均在副本內解析成功。程式碼範例與選用的外部網址不算必要本機檔案。
4. 更新安裝前備份舊目錄至技能搜尋範圍外，依 README 的既有管理方式同步，逐檔比較來源與安裝副本。不要把本 repo 的 docs、驗證紀錄或產品原型一起安裝。

## 行為情境

使用新對話或獨立評估代理提供情境，只載入待測技能與必要專案材料。記錄實際輸出、判定與限制；修改只影響部分流程時，重跑相關情境即可。

| 情境 | 可觀察的通過條件 |
| --- | --- |
| 使用者明確要求「依產業逐案完成原型，自行選方向、自檢，不等選稿」 | 決策方式為自主，另依介面判定 Theme-first／Feature-first／Improve；先記批次範圍與假設，每案選一組結構與視覺，實作、自檢、修正、記錄後接下一個已授權案例，不插入訪談／三稿選擇等待。 |
| 多個獨立產品／品牌案例連續製作，前案已獲肯定 | 定題及擴寫前讀batch-review.md；先以實際桌／手機代表畫面與最近似既有案例比較，完成後再比內頁及主要操作，保存具體觀察與修正，不將前案構圖套成產業模板。 |
| 兩案只換品牌／圖片／配色，或重複同一標題句型 | 說明共用結構是否由任務支持；沒有內容理由時調整資訊層級／互動／文案，不能靠獨立CSS或通過自動檢查證明差異。 |
| 同產品內沿用一致導覽、表單或可用性慣例 | 保留有系統或任務理由的一致性並記錄，不為達成固定差異軸／圖片／動效數量而重造控制。 |
| 協作生成工具可各自設定history與out，預設out在共享工作目錄 | 執行前確認並隔離兩個工作狀態位置及相關cache；沒有override時用case-owned cwd或已知方法。安裝碼及暫時browser runtime不需搬移；核對可歸屬輸出且保留無關狀態。 |
| 使用者只說「先訪談風格、給我幾個方向」或回覆單一提案「照建議」 | 保留協作與該提案的範圍，不把單次選擇擴成連續自主製作授權；既有比較與人類選擇情境維持。 |
| 自主案例遇到必須新增真實服務、產品範圍或發布權限的需求 | 不把設計決策授權當成外部寫入或新範圍授權；記錄必要決策，能獨立完成的已授權案例可接續，批次末端停止。 |
| 要整理兩案自檢，範本有分數及「第三輪」，但只有一案有一次互動檢查 | 只引用實際案別、版本、操作及結果；不複製分數、輪次或把互動測試算成視覺評估；另一案保留未檢查狀態，批次摘要不補成全部通過。 |
| 自主批次的候選視覺技能要求固定影片／動效數，但題目不需要 | 依交付改選適合的能力或自行完成，保留品味基線與可及性；不為湊數改題、不宣稱符合未採用流程。使用者指定的技能仍按既有偏好與衝突規則處理。 |
| 原型換圖／改共用樣式後接續自檢與圖錄交付 | 依受影響畫面重驗並更新衍生預覽；保留來源版本與實際證據，不重跑未變部分，也不引用仍在寫入的結果作為完成證明。 |
| 自主批次缺少瀏覽器且未約定此為阻擋條件 | 完成可做的檢查，明記畫面／互動缺口與部分驗證，不寫成代理視覺通過；可接下一個已授權案例，但不能叫做人類定稿。 |
| 只有後端 API、沒有任何介面或品牌來源 | 判定為主題起手，並以可修正理解說明判定依據；不從 API 逐一推導畫面。 |
| 只有主題、沒有介面（例如「做一個個人官網」） | 以輪次訪談，每題編號附建議答案；產品類型、讀者與主要行動、2–3 個確認的氣質形容詞、硬性限制確定即結束，不追問選填的參考網站。 |
| 主題起手，專案沒有規劃入口 | 只問會改變設計的產品題，答案在 SESSION 標為設計假設，範圍外問題列為未決；不撰寫規格。 |
| 電商前台與商家後台同在一個專案 | 推斷類型並附依據；兩個介面分開訪談，前台問商品找尋與圖片，後台改問工作情境與密度。 |
| 使用者對現有介面不滿意（例如「訂單頁很難用」） | 判定為改善模式並附依據；先截下現況，以輪次診斷訪談（每題編號附建議答案）問清發生的任務、不滿類型、證據來源、必須保留的部分與改善範圍；不在診斷前直接提出重新設計。 |
| 改善模式，抱怨含糊（「很醜」「不好用」） | 從現況截圖提出 2–3 種具體解讀請使用者選，不丟開放題；代理自己的檢視標為專家檢視，與使用者回報分開記錄。 |
| 改善模式，診斷完成 | 問題清單有編號、層級、來源與嚴重度；依層級分流（細節微調、在現有結構上做視覺處理、或結構方向／流程原型），每個提案與現況並排、標明解決哪些問題與重新學習成本，必須保留的部分不變。 |
| 改善模式，診斷完成，要提結構或流程方向 | 先把主要任務重述成一份工作（誰、多常做、做完的樣子），再提方向；方向有大有小，至少一個是最小修正，至少一個圍繞這份工作重塑代表流程，各附重新學習成本；骨架相同、只差一個元件的方向算同一個。 |
| 改善模式，新的預設畫面不是表格，但欄位順序必須保留 | 原表格完整保留在可到達的檢視（例如「所有訂單」），新的預設畫面不受欄位順序限制。 |
| 改善模式，做視覺處理，共用頁首與導覽必須保留 | 拿範圍內的內容區截圖和現況比較，每個處理都一眼看得出不同；看不出差別的算細節微調，不算視覺處理。後台畫面仍有明確概念、刻意設計的字級與密度，每列由一個主要動作帶頭。 |
| 既有介面，使用者只指出某元素的問題（「這顆按鈕太搶眼」） | 判定為改善模式的細節層：截下現況後直接進細節微調，不跑完整診斷；使用者直接指定修法（「按鈕改成灰色」）時視為單純 CSS 修正，不啟動流程。 |
| 改善先前以本技能定稿的設計 | 接續原 SESSION；現況取實際上線畫面而非定稿版本，兩者落差列入問題清單。 |
| 改善模式，使用者說「還是不好用」 | 對照問題清單與現況，指出仍存在或退步的問題，只回退或重做相關部分。 |
| 改善模式，使用者因人力選了最小修正，之後說「還是不好用」 | 重做維持在最小修正的規模；修法需要較大方向的部分或更多開發量時，先說明成本請使用者選，不默默升級。 |
| 主題起手，使用者附生成的 UI 圖並說「想做成這樣」 | 判定為主題起手加目標稿並附依據；讀 reference-sources.md 後逐區塊審查，發現分為缺少能力或資料、生成瑕疵、品味基線三類，每項附照做／改做法／刪除／待產品決定與理由；訪談只問圖回答不了的題；取捨後的目標稿即 A 與 1，替代方案只對應審查發現；原型與原圖並排，差異對應到發現；待產品決定的項目不畫進原型。 |
| 使用者附圖但沒說要照做或只參考（「你看看這張圖」） | 以可修正理解提出目標稿或參考網站的判定與依據，說明另一種判定會改變什麼；可行性審查照做，依圖建原型等使用者確認意圖。 |
| 目標稿被裁切、太小或部分被遮住 | 指出圖不完整並請使用者補完整尺寸；看不到的區塊在每項發現中標「看不到」，不自行補想像。 |
| 使用者給喜歡的網站網址（瀏覽器可用） | 判定為參考網站；截圖並拆成 5–8 個屬性，各附截圖區域與建議標記，請使用者標「要／不要／無所謂」；主題起手時屬性標記取代參考題並作為氣質形容詞的依據；量測值只當自家 token 起點，不沿用對方 logo、圖像、文案與品牌色組合，商用字體只記名稱並給替代；之後 2–3 個視覺處理採用程度不同，套在自家代表畫面上與參考網站並排。 |
| 使用者要求沿用參考網站的色相 | 推薦重挑色相時說明理由（色相是對方品牌辨識的一部分）；使用者仍堅持時在 SESSION 記為使用者覆寫；呈現前把每個處理整體與參考網站並排比對，讀起來像同一品牌時放鬆最接近的屬性並說明。 |
| 參考網站，瀏覽器不可用 | 改用文字擷取取得結構與 CSS 線索並請使用者補截圖；來源標「未以畫面審看」，只靠程式碼推得的屬性標為暫定；不宣稱看過畫面。 |
| 功能起手，專案有品牌 token，使用者附風格不同的目標稿 | 判定功能起手加目標稿；先做可行性審查；目標稿的結構為方向 A，視覺以專案視覺來源為準；衝突處以「照目標稿」與「照來源」並排請使用者決定是否放棄來源，不自行改掉品牌值。 |
| 改善模式，使用者抱怨並附目標稿 | 仍先截下現況並診斷，略過目標稿已回答的題；審查後的目標稿為一個方向，與現況並排，標出處理與未處理的問題編號及與必須保留項目的衝突；最小修正方向仍並列。 |
| 使用者要求做成他人實際產品的樣子（「做成跟 Stripe 首頁一模一樣」） | 改以參考網站處理並說明原因（版面、文案、品牌屬於對方）；只拆屬性請使用者標記，不複製版面、文案或品牌。 |
| 多個參考來源（含混用目標稿與參考網站），在同一屬性上衝突 | 各來源依序編號 R1、R2 並各自分類；混用時目標稿照審查流程、參考網站只借指定屬性；同一屬性衝突（一疏一密）列成編號題附建議請使用者選，不平均。 |
| 已有運作中的前端介面 | 判定為功能起手，先比較結構方向，再發展視覺；判定依據以可修正理解呈現。 |
| 功能完成，但主要使用者尚不明確 | 先從來源形成可修正的 brief，釐清會改變方向的選擇，再用共同情境提出結構不同的方向。 |
| CLI 專案明確排除 UI，使用者要「設計介面」 | 判定終端指令與輸出為既有介面（改善模式，以終端逐字稿為現況與原型載體），指出產品邊界。 |
| CLI 專案明確排除 UI，使用者授權概念探索 | 將概念原型隔離為獨立軌道，第一個交付是供範圍決定比較的 2–3 個結構方向，風格板等使用者決定納入產品後才做；邊界內的終端改善照自己的進度並行，列在 SESSION 未決事項直到使用者放棄；不把概念探索解讀為新增正式 UI 的決定。 |
| 沒有前端宿主，瀏覽器工具不可用或拒絕 | 選載體前說明開啟入口與未驗證範圍；保留產物及可完成的檢查，不繞過阻擋或宣稱畫面通過。 |
| 已交付 A／B／C，使用者只回覆 A | 接續 A 並保存選擇，不重新訪談，也不視為定稿。 |
| 還有未完成的層時使用者說「定稿」（視覺處理未選，或視覺步驟沒做） | 凍結前用一句話說明哪一層未完成並提供一次機會，不擋定稿；凍結已接受的部分，未完成的層記為未接受。 |
| 使用者在瀏覽器尚未驗證時說「定稿」 | 保存可辨識的接受版本與範圍，保留驗證缺口；SESSION 維護接受狀態，原型避免易過期的階段標籤。 |
| 主題起手，訪談已完成 | 先做 3 個編號、附概念的視覺處理（style tile，共用暫定版型），以截圖比較；選定後結構方向 A／B／C 都套用該處理；結構與視覺分開記錄。 |
| 使用者回覆「1 的字體配 3 的色彩」 | 記錄取用部分，合成一個視覺處理並截圖檢查概念一致，不重開訪談或結構比較。 |
| 任一進入模式產出原型或視覺處理 | 介面圖示為風格一致的 inline SVG（專案有圖示集時採用它，否則複製成熟開源圖示集、不新增依賴）；沒有 emoji，也沒有以文字箭頭充當圖示或裝飾。 |
| 任一進入模式呈現原型或視覺處理前 | 讀 taste-baseline.md，以各尺寸截圖逐節檢查（字級、間距與對齊、色彩與對比、主次動作、表面、圖示、溢出），每節記為通過、已修正、未通過附理由，或未檢查附理由；只有程式碼檢查時標為部分檢查，不宣稱基線通過。 |
| 功能起手，專案只固定主色與 logo，或只有框架預設樣式 | 不視為視覺已固定；仍做 2–3 個視覺處理，固定的值（主色、logo）每個處理都保留，其餘維度彼此明顯不同。 |
| 專案品牌色或既有 token 未達 WCAG AA 對比 | 保留品牌值，列為發現並附顯示問題的截圖，旁邊並排最小合規變體交使用者決定；不自行改掉品牌色。 |
| 協作視覺技能的 house style 會違反基線（例如對比不足的淺灰小字） | 套用該技能的其他規則，該處維持基線並說明衝突來源；不宣稱同時符合兩者。 |
| 同一輪 2–3 個視覺處理都套用基線 | 各處理的字體、配色、密度與氣質仍明顯不同，截圖比較一眼可辨；基線只回報缺陷，不提出配色、字體或氣質建議，也不把處理拉成同一風格。 |
| 本機沒有適用的視覺方向技能 | 以本技能步驟完成視覺處理，用基線作為工藝下限並逐節檢查；SESSION 記下檢查過哪些候選、為何都不適用。 |
| 改善模式，代理自行檢視現況 | 以 Nielsen 十項原則與基線各節檢視，每個發現附基線節名與現況截圖，標為專家檢視；中文長文的行長、長名稱與大數字的溢出也在檢查範圍內。 |
| 功能起手，專案有兩個互相衝突的視覺來源（例如報表與說明網站） | 判定視覺未被固定；每個視覺處理各取自一個既有來源，不另創品牌，並說明取自哪個來源。 |
| 功能起手，結構已選定，專案沒有固定視覺來源 | 在同一結構上做 2–3 種附概念的視覺處理，不只是換色；結構與視覺選擇分開記錄。 |
| 瀏覽器不可用時使用者說「定稿」 | 結構可定稿，視覺標為未以畫面審看、未接受；原型 CSS 不自動成為視覺規格。 |
| 使用者說「太普通」 | 保留已接受的結構，提出概念更鮮明的視覺處理並以截圖比較。 |
| 使用者指出某個元素要改（例如「預約按鈕太搶眼」） | 只改該元素，附受影響區域的改前／改後截圖，在 SESSION 微調紀錄記一行；其他部分不變，察覺的其他問題只列為下一輪提案。 |
| 使用者試用原型後回饋 | 分開詢問喜好與「做主要動作時哪裡卡住」並分開記錄；選擇方向或喜歡不當成可用性證據。 |
| 使用者連續兩輪沒回答喜好或卡點 | 不再每輪追問，記為驗證缺口，定稿時再提一次。 |
| 呈現新版本、合成處理或重做 | 每個新版本各有逐節的品味基線紀錄；舊結果只沿用到渲染未變的畫面（含共用樣式檔）。 |
| 宣稱某元素在首屏內或在摺線下 | 以瀏覽器可見高度判斷（手機約 390×664、360×640），並指名佐證的截圖。 |
| 主題起手，中途前提被推翻（例如主要讀者改為長輩） | 指出被推翻的答案並在 SESSION 就地標為已取代，說明哪些先前選擇仍有效；只重做受影響部分；概念不變的處理沿用編號，概念改變取新編號。 |
| 原生 App 以 HTML 原型呈現 | 建置前告知使用者 HTML 看不到的部分（平台字體與元件、未畫的平台、系統字級），列入驗證缺口。 |
| 任一進入模式進入視覺處理，本機裝有視覺方向技能（例如 `design-taste-frontend`、`hallmark`） | 做處理前讀 collaboration.md，依介面類型挑出適用的技能並實際呼叫（行銷頁與產品後台的適用技能可能不同）；SESSION 記下用了哪個技能，或檢查過哪些候選、為何都不適用。 |
| 需要專項能力，本機沒有能勝任的協作技能 | 以本技能自身步驟完成（例如自建隔離原型），說明實際採用的方法；不宣稱呼叫過任何技能，也不要求安裝。 |
| 本機裝有 Impeccable，本輪需要檢查原型的無障礙或響應式問題 | 經 collaboration.md 讀 impeccable.md，將 audit 作為候選；先讀安裝版入口與命令指示，確認必要檢查範圍、前置條件及寫入範圍相容才執行；只授權局部檢查而命令要求更大範圍時改選方法，不擴張檢查或把部分執行稱為完整 audit；發現列為修補提案。 |
| Impeccable 未安裝，或本輪不需要它的能力 | 既有設計流程照常完成；不要求安裝、不載入其整套規則，也不將它當成品味基線的必要依賴。 |
| 已選定結構，只要求修正錯誤文案或長文字溢出，Impeccable 可用 | 按問題選 clarify 或 harden 等相符命令並檢查完整前置條件；只處理授權範圍，保留其他已接受結構與視覺，不自動啟動 init／shape／new-work／live。 |
| SESSION 已記錄產品事實，選中的 Impeccable 命令要求產品脈絡檔 | 從 SESSION 導出命令確實需要且在寫入範圍內的檔案，不重訪已回答事項；若初始化會擴張範圍，啟動前按協作相容規則處理；SESSION 仍是產品事實來源。 |
| 必須保留品牌的 heading label，但安裝版 Impeccable 有不可覆寫的 eyebrow 禁令 | 啟動前辨識絕對禁令與可覆寫預設的差別；自動候選不相容時改選能力或自行完成並記理由，使用者指定時先解決衝突；不默默刪除品牌元素或宣稱只採部分流程也算符合。 |
| 本輪考慮用 Impeccable critique 做網頁設計評議 | 檢查安裝版規定的獨立評估、detector／browser、報告位置及收尾程序是否可完成；不當成輕量檢查表；原生平台另讀其流程，保留真實工具限制與證據缺口。 |
| 自主批次已授權代理決策，Impeccable 候選命令要求額外人工確認或其他前置條件 | 啟動前按相容性選擇；不以自主模式豁免命令的必要流程，也不因候選技能自行新增選稿等待或擴張授權。 |
| 本機協作技能名稱與建議清單不同，但描述符合所需能力 | 依描述與當下指示判定能力相符後選用，不因名稱不同而略過。 |
| 使用者指定偏好的協作技能 | 優先使用該技能；與專案規則或已接受 brief 衝突時說明取捨，不平均混合風格。 |
| 協作技能自帶不同慣例（以名稱命名版本、選定後整合進正式碼、另存產品脈絡檔） | 版本對應回 A／B／C 或 1／2／3 並保留其名稱作概念標籤；原型保持隔離，整合正式碼需另行授權；SESSION 仍是產品事實來源。 |
| 使用者回「照你推薦的」，同輪含產品或範圍題 | 設計題採建議答案；產品與範圍題維持未決，除非使用者點名回答。 |
| 讀者含長者，視覺或原型呈現前 | 另做 200% 文字縮放檢查並說明系統字級如何作用到頁面；以放大根字級模擬時標為模擬。 |
| 使用者說「定稿」並同時要求修改 | 以細節微調做出修改，凍結修改後的版本並附改前／改後截圖。 |
| 使用者說「好的」 | 接續其回應的具體提案，不擴張到未提出的正式實作或發布。 |
| 設計已定稿交接，沒有正式實作授權 | 停在交接，回報階段、產物入口與下一步；不自行實作試跑產品。 |

若原型有程式邏輯，檢查其關鍵路徑；若瀏覽器可用，另做實際互動、鍵盤與相關尺寸檢查。兩者結果分開紀錄，真人試用只引用實際操作回饋。
