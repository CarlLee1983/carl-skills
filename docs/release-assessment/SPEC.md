# release-assessment 共用 skill 規格

狀態：定稿。此文件是後續實作與驗收依據；本次交付不包含 skill 安裝或任何實際發布操作。

## 目的與範圍

建立跨專案共用的 release-assessment skill，獨立判斷變更是否需要納入版本、累積變更應如何調整版本，以及目前是否適合發布。合併 PR 本身不構成發布理由或發布授權。

共用 skill 負責蒐集證據、分析與提出建議。各專案維護自己的發布政策。適用於套件、CLI、網站服務與 monorepo，支援 SemVer、日期版本與沒有對外版本的專案。

當評估支持後續操作時，skill 提出具體方案並詢問使用者；取得對應授權後，依專案既有流程協助升版、建立 tag 或發布。

## 評估對象

| 名稱 | 定義 |
| --- | --- |
| 本次變更 | 使用者指定的 PR 或提交範圍，用於判斷是否需要納入下一個版本。 |
| 發布單位 | 可獨立交付的套件、CLI、服務或一組統一發布的元件。 |
| 基準 release | 該發布單位與目標發布通道對應的上一個 release，包含可驗證的提交位置。 |
| 目標提交 | 本次評估固定使用的候選提交；報告記錄 SHA，避免分支移動造成歧義。 |
| 發布候選 | 自基準 release 到目標提交的完整累積變更，用於版本與發布條件判斷。 |
| 專案政策 | 專案對版本、公開契約、交付內容、發布節奏與必要檢查的明確規則。 |

尚未合併的 PR 可提供條件式預估，但須與實際發布候選分開。首次發布或找不到可信基準時，依專案初始版本政策處理；資訊不足時明列缺口。

## 三項獨立判斷

| 判斷 | 輸出 | 判斷依據 |
| --- | --- | --- |
| 本次變更是否需要納入下一個版本？ | 需要／不需要／資訊不足 | 對交付內容、行為或公開契約的實際影響，以及是否已被交付。 |
| 相較基準 release，版本如何調整？ | 不變／patch／minor／major／依專案策略／不適用／資訊不足 | 整個發布候選的累積影響與專案版本政策。 |
| 現在是否適合發布？ | 可發布／累積到下次／被阻擋 | 必要條件、證據完整性與專案發布節奏。 |

每項判斷均須附理由、證據位置與相關資訊缺口。某項資訊不足，只影響依賴該資訊的結論，不抹除其他已有證據支持的結論。

### 版本判斷

SemVer 專案依公開契約判斷：不相容變更為 major、向下相容功能為 minor、向下相容修正為 patch；無須調整版本才使用「不變」。0.x、預發布與其他例外依專案政策處理。

日期版本使用「依專案策略」，列出可確認的候選版本與規則；沒有對外版本時使用「不適用」。不知道如何調整時使用「資訊不足」，不能寫成「不變」。

以發布候選的最終有效差異及必要轉換影響為準，檢查撤銷、替代與重複變更，不能僅將提交標籤中的最高級別當成結論。

### 發布條件與節奏

- 被阻擋：必要驗證失敗、未完成、證據過期，或缺少足以判斷發布安全與政策符合性的必要資訊。另列通過阻擋後適用的節奏建議。
- 累積到下次：必要條件已滿足，但政策要求累積、等待固定窗口，或目前沒有需要交付的新變更。
- 可發布：必要條件已滿足，且目前符合專案發布節奏。這是建議，不是操作授權。

若同時存在阻擋與等待窗口，以「被阻擋」為主結論，分別保留兩者原因。

## 證據蒐集流程

1. 確認使用者指定的本次變更、目標分支或提交、發布單位與通道；將可移動的參照解析為固定提交。
2. 讀取專案指引與發布政策，檢查版本檔、changelog、打包或部署設定、release workflow 與必要檢查。記錄權威來源及互相衝突的規則。
3. 確認基準 release 與實際交付狀態；tag 不自動等同已發布，依專案流程查證。
4. 閱讀 PR 實際 diff、相關呼叫端、公開契約與測試，並涵蓋基準到目標提交的全部變更。PR 標題、feat/fix 與 changelog 僅為線索。
5. 將累積變更對應至發布單位，分析相容性、交付影響與必要相依連動。
6. 查核測試與發布檢查結果所對應的提交及執行環境。無法確認適用於候選的結果不得列為已通過；缺乏工具或權限時保留缺口。
7. 按三項判斷產出報告。只有取得足夠證據的結論才使用確定語氣；推定須標明，並指出如何驗證。

文件變更須檢查交付方式：隨套件打包、生成公開契約或構成交付產品的文件可能需要發布；僅供內部開發的文件不能單憑檔案副檔名決定升版。建置與相依更新也以產物及行為影響判斷。

找不到專案政策時，先從現有設定與文件蒐集可確認的事實，列出推定和缺漏；相容性承諾與發布節奏由專案決定。來源衝突且會改變結論時，詢問使用者，不默默選用方便的來源。

## 專案政策範本

建議以專案根目錄的 `RELEASE-POLICY.md` 作為入口；已有權威文件時，以連結引用，避免維護兩份相同規則。以下欄位可使用文字或表格，無須引入設定解析器。

```markdown
# 發布政策

## 發布單位與交付內容
- 名稱、路徑、交付型態與產物：
- 文件是否隨產物交付：
- 發布目的地與通道：

## 版本策略
- SemVer／日期版本／沒有對外版本：
- 版本權威來源與更新方式：
- 基準 release 的識別方式與初始版本規則：
- 0.x、預發布與其他例外：

## 公開契約
- 承諾相容的 API、CLI 參數、設定與資料格式：
- 相容性判準、棄用與遷移規則：

## 發布節奏
- 逐次／累積／固定週期，以及觸發條件：
- 緊急修正或其他例外：

## Monorepo（適用時）
- 統一版本或獨立版本，以及發布群組：
- 相依套件的版本與發布連動規則：

## 發布流程與必要檢查
- 既有發布文件、workflow、版本工具與 changelog 規則：
- 必要檢查、適用提交及可接受的驗證結果來源：
- 升版、建立 tag、發布各自的既有步驟：
- 失敗恢復或撤回流程：
```

Monorepo 逐發布單位輸出三項判斷，再彙整共同阻擋與發布順序。統一版本按既定群組評估；獨立版本檢查相依影響。政策不明時，不假設整個 repo 一起升版，也不另創版本連動機制。

## 報告格式

先以一句話交代版本與發布建議，再提供下列資訊；多發布單位可用表格呈現。

```markdown
建議：下一版升 minor；目前被阻擋。

- 評估對象：發布單位、通道、本次變更、基準 release、目標 SHA。
- 納入下一版：需要。新增向下相容的 CLI 選項。
- 版本調整：minor。完整候選另含兩項修正。
- 發布時機：被阻擋。必要驗證尚未完成。
- 節奏建議：驗證通過後，依專案政策累積到下次發布。
- 證據：實際 diff、政策、檢查結果與發布設定的位置。
- 缺漏與下一步：補齊指定驗證，再重新評估受影響結論。
```

## 操作提案與授權

評估完成後，若符合下一步條件，先查看專案相關資訊並準備可審閱的操作提案。提案列明發布單位、目標提交、版本、預計修改檔案、tag、目的地、操作順序、必要副作用與尚待滿足的條件，再詢問使用者。

授權分為升版、建立 tag、發布，也可由使用者一次明確同意列出的整套操作。同意升版不代表同意建立 tag 或發布；需要 commit、push 或觸發遠端 workflow 時，須將這些行為明列於提案並納入授權範圍。

暫不發布時，若政策允許，可詢問是否先準備升版。被阻擋時，先提出補齊驗證或其他可行準備工作；使用者同意不能取代必要檢查。

取得同意後，沿用專案既有工具與流程執行。動作前重新核對目標與前置條件；若版本、提交、目的地或重要影響超出原提案，更新提案並取得差異部分的授權。原範圍仍有效時不重複詢問。

完成後查證版本修改、tag 指向、workflow 與實際發布結果，區分本機完成、遠端已建立、執行中、發布成功與失敗。部分成功時記錄已完成動作及恢復建議，不盲目重跑或宣稱整套成功。保留無關的未提交工作與既有歷史。

## 驗收案例

| 情境 | 必須觀察到的結果 |
| --- | --- |
| 新增相容 CLI 選項，候選另含兩項修正，必要驗證未完成 | 納入需要、minor、被阻擋；另列通過後的節奏建議。 |
| 本次只改內部文件，但候選另有未發布修正 | 本次可不需要納入；候選仍可需要 patch，不以本次 PR 取代累積評估。 |
| 文件隨套件交付且政策要求發布 | 依實際交付影響判斷需要及適用版本，不能一律忽略 docs。 |
| PR 標示 fix，但移除承諾相容的公開參數 | 依實際 diff 與政策判定不相容，不能僅憑標籤給 patch。 |
| 必要檢查通過，但採固定週期且窗口未到 | 累積到下次，不能因 PR 已合併就建議立即發布。 |
| 已到發布窗口，但必要檢查失敗 | 被阻擋，列明失敗證據。 |
| 日期版本或沒有對外版本 | 分別使用依專案策略或不適用，不硬套 SemVer。 |
| 版本或相容性政策缺漏 | 相關判斷資訊不足；保留其他可確認結論，列明所需決策。 |
| 獨立版本 monorepo 僅部分單位受影響 | 分別評估，依既定政策檢查相依連動。 |
| PR 尚未合併 | 條件式預估與實際候選分開，不聲稱已包含於發布內容。 |
| 基準不存在、無法取得完整 diff，或檢查只對應舊 SHA | 明列證據缺口；不足以判斷發布條件時標示被阻擋。 |
| 功能已在候選中完整撤銷 | 檢查最終差異與殘留影響，不僅憑 feat 記錄升 minor。 |
| 使用者只同意升版 | 僅執行獲准範圍，不能順便建 tag、push 或發布。 |
| 使用者同意整套提案，目標與條件未改變 | 依序執行並驗證，不在每一步重複索取相同授權。 |
| 同意後目標提交或發布目的地改變 | 重新評估並取得變更範圍的授權。 |
| 發布部分成功或 workflow 尚在執行 | 如實回報已完成及待完成狀態，避免重複發布。 |

## 後續實作交付與完成條件

實作交付為可跨專案安裝的 `skills/release-assessment/SKILL.md`、按需載入的專案政策範本與驗收案例。核心流程保持專案無關，專案特殊規則留在其權威政策文件。

完成須能逐案驗證三項結論、證據追溯、缺漏處理與操作授權邊界。範例及模擬流程即可測試授權分支，驗收不需要真的發布套件或服務。安裝、提交、推送與實際發布不是本次規格定稿的完成條件。
