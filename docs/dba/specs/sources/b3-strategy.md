## B3 驗收證據與測試環境策略 — 最終確認稿（待全文確認，尚非 Resolution）

本稿整合 wayfinder 訪談 Q1–Q9 已確認的決策；第三輪 Q7–Q9 由使用者回覆「全部照建議」確認。具體化 [B3 原生權限與生產變更治理工作流程規格](https://github.com/CarlLee1983/dbcli/issues/253#issuecomment-6259121225) 的驗收策略，沿用其必要主張、判定優先序、有限觀察、停止條件、人工批准與交接，不重開已核准行為。

本票只決定驗收策略，不表示 Skill 已實作、環境已具備或測試已通過；不授權建置、改權限／憑證、DDL、故障注入、復原、清理或發布。全文仍待使用者確認。B1／B2 可共享適用證據，但不能替代 B3 驗收。

### 1. 分階段驗收與聲明

- **行為候選版**：全部 19 類 B4 情境及必要分支的實際 Skill 行為案例通過，才可稱「B3 行為驗收通過，實環境驗收未完成」，附逐項缺口。尚未全部通過只能報告進度。
- **完整 B3 驗收**：行為驗收、下列最低實環境／人工／客戶端證據、可追溯性、所屬 repo 所需 gates，以及對同一候選內容的人類驗收審查均完成。聲明明列實際引擎、版本、儲存引擎、部署形態、操作及客戶端範圍，不推廣到未驗組合。
- **發布授權**：與驗收分開，本票不授權發布。

行為測試 PASS／FAIL、單一 DBA 主張 met／not-met／blocked／indeterminate、實環境覆蓋三者分開記錄。正確判出 not-met、blocked 或 indeterminate 可以讓相應行為測試 PASS，不能證明資料庫主張 met，也不能抵銷必要實證缺口。未執行不得算 PASS；部分環境已驗收可逐項陳述，整體仍保留未完成狀態。

完整驗收證明工作流程依契約運作，不承諾每個受評資料庫均符合政策。但本稿明列的正常 DDL、設定套用與憑證更新成功路徑，仍須有相應正向實證，不能僅以正確識別失敗替代。

### 2. 證據分工、版本與部署覆蓋

| 證據層 | 用途與最低範圍 |
| --- | --- |
| F：可重跑的合成案例／fixture | 覆蓋所有 19 類情境及必要分支，驗證真正 Role Skill 的判讀、工具選擇、停止、交接及結果呈現。合成資料不能證明真實權限、TLS、DDL 或 RDS 行為。 |
| L：隔離自管引擎實證 | PostgreSQL、MySQL、MariaDB 各一組完整版本基線，涵蓋下節權限、TLS 與原生 DDL 實證。可用隔離本機／容器；只驗引擎層。 |
| R：真實 AWS RDS 實證 | 三引擎各一組完整版本基線，包含受限帳號／受管角色、平台觀察、pending 到生效，以及憑證更新成功路徑。合格歷史事件可按適用性抵用。 |

六組基線是覆蓋要求，不是六個同時常駐資源，也不是只需六次工具呼叫。可分時使用、共用 B1／B2 環境；每項 B3 所需觀察與判定仍須有自己的證據對應。

後續人選定的 Story 開始時，依實際支援情況固定完整引擎版本、區域、部署形態、相關設定、帳號與角色範圍、dbcli／AWS CLI／capability contract，以及指定客戶端／驅動的名稱與版本。L／R 不要求相同 patch。每個 DDL 案例另記適用的儲存引擎、具體操作及 ALGORITHM／LOCK 條件；不把 MySQL 與 MariaDB 的語意或證據互換。

不做版本×部署×儲存引擎×操作×客戶端的完整交叉組合。只對實測組合聲明通過；其他版本、儲存引擎、部署及客戶端保留未驗收，新增組合依影響補證。B2 已驗 instance／cluster 切換，不代表該部署的 B3 設定、憑證或 DDL 已驗收。

平台層限 AWS RDS，不含 Aurora。自管平台層、其他雲平台維持既有範圍界線，相關平台主張 indeterminate 並交接給人；不否定可評估的引擎層主張。

### 3. 各操作族的最低實證

#### 3.1 原生權限

三引擎 L 各以預定受限蒐證帳號完成一次權限稽核，涵蓋適用的直接授權、角色繼承／啟用、owner、PUBLIC、預設權限、高權與管理／再授權能力。依已確認的用途與基準比較，不將直接 GRANT 清單當成完整有效權限分析。

各有人工授予／撤銷權限前後的實際效果，使用隔離、可拋棄的對象與身分，保留允許及拒絕存取證據，按版本與帳號適用語意核對既有／新連線。必要應用／管理存取由指定人工執行者驗證並交回證據，不能由授權命令成功推論存取正常。

三引擎 R 各保留受限帳號正常取證、安全權限不足案例，以及實際受管角色與可見性限制；不要求把 L 全部授權組合在 R 重演。RDS IAM 與引擎原生權限分列，不能互證。高權帳號成功不能替代預定受限帳號，受限帳號成功也不直接證明最小原生權限。

管理者鎖出、應用故障及缺證據分支以 F 驗證，不要求鎖死真實管理帳號。額外身分或可能寫入的允許／拒絕探測，事先列入批准計畫並交人執行；agent 不改帳號、升權、撤權、建立備援存取或試做未授權寫入。

#### 3.2 TLS、RDS 套用及憑證

三引擎 L 各具指定客戶端／驅動的加密、CA 信任、主機名驗證成功證據，以及安全的不受信任憑證、主機名不符等拒絕案例。可引用適用的 TLS Tool 驗收證據，但必須核對候選版本、設定與實際證明範圍；dbcli 自身的 TLS 測試不能替代其他指定應用客戶端的證據。

三引擎 R 各具下列兩條路徑：

1. **至少一次設定 pending → 實際生效**：連結同一資源的要求值、pending／套用狀態、人工操作及引擎生效觀察。保留各時點與來源語意，不把期望設定或平台已接受當成引擎已生效。
2. **至少一次憑證更新成功**：連結批准及人工執行、平台憑證／CA 與適用的引擎觀察、指定客戶端有效信任與主機名驗證設定、變更後新連線／重連，以及事先選定的必要應用可用性證據。舊連線正常、CA 有效或設定成功均不能單獨替代整條證據鏈。政策要求拒絕非 TLS 時，另有安全的拒絕證據。

兩條路徑可以由同一事件滿足，但證據必須分別充分；不要求每種 parameter 或部署形態都重演。合格歷史事件可抵用。缺少路徑、指定客戶端或必要應用證據時保留缺口，不能只靠觀察目前設定宣稱成功路徑已驗收。

輪替失敗、大量客戶端不信任、錯誤套用與恢復失敗以 F 覆蓋；安全的憑證／主機名拒絕可在 L 驗證，不要求在 RDS 製造憑證事故。連線加密、強制 TLS、客戶端身分驗證及 RDS 憑證狀態分別判定，不彼此替代。

#### 3.3 原生 DDL 與受控失敗

| 操作／情境 | 最低實證 |
| --- | --- |
| 正常原生 DDL | 三引擎 L 各至少一次完整人工變更鏈：前置證據、鎖等待／操作／影響與觀察預算、復原方案、有效批准、實際執行、schema／物件有效性、適用資料不變條件／應用／負載／複製驗證及收尾。 |
| PG concurrent index 失敗與 INVALID 殘留 | L 小型隔離物件真實重現至少一次，保存失敗及實際索引有效性／殘留觀察，人工依批准計畫清理並驗證。 |
| MySQL／MariaDB 多步操作部分完成 | 兩引擎 L 各至少一次真實案例，按實際版本／操作確認提交邊界與物件狀態；MySQL 證據不能替代 MariaDB，不宣稱整批已 rollback。 |
| 鎖等待／長交易 | 三引擎 L 各至少一次有限、受控的隔離案例，驗證取證與停止邊界；記錄觀察預算，不要求耗盡鎖或服務資源。 |
| 高負載、空間不足、複製超標、斷線後結果未知、危險重試、復原／清理失敗 | 失敗分支可由 F 覆蓋，不為驗收耗盡資源或製造事故；不能因此宣稱真實重現這些失敗。 |

正常變更與部分完成可在同一演練中使用不同操作，但各自必須有足夠證據。RDS 不必重演整套 DDL 故障；L 實證不能宣稱 RDS DDL 組合已實測。

所有新演練在隔離環境由人依批准計畫執行，停止操作、終止 blocker、復原與清理亦交人。agent 僅作計畫內唯讀觀察，不自動降級演算法、延長預算、換工具或重試。SQL 查詢逾時不冒充 DDL 伺服器端鎖等待控制；失敗／斷線不證明未產生變更。具體復原適用性沿用 B3，只有備份存在不構成可復原本次變更的證據。

### 4. 十九類 B4 情境與證據對照

每列及必要分支均須 F；L／R 欄是額外實證門檻，不能由 F 補成實環境事實。不是一類只做一個案例；按原 B3 的判定及停止邊界展開。

| B4 情境 | F 必須驗證的行為與分支 | L／R 的必要實證與限制 |
| --- | --- | --- |
| 1. 必要主張證據齊全、適用、無矛盾 | 只宣稱固定範圍符合；未選項仍未評估，就緒不等於已執行；不得事後縮小範圍 | L／R 各操作族的完整證據鏈；每個主張按實測結果判定 |
| 2. 缺權限／TLS 基準、例外過期或基準不適用 | 缺乏可比基準 indeterminate；充分違反有效政策 not-met，各分支分開 | 實證有已確認基準、例外及時間；不故意讓真實例外過期 |
| 3. 直接 GRANT 正常但繼承／PUBLIC／owner／高權／預設權限不同 | 按引擎語意揭露可達權限與未來物件差異，不報完整有效權限分析 | 三引擎 L 適用授權來源與人工授予／撤銷前後證據；R 受管角色及限制 |
| 4. 僅自身可見、NULL／空集合、無權、blacklist 省略或查詢失敗 | 各原因分開；不可見不當不存在／符合，不升權或收集秘密 | L／R 受限帳號正常取證及安全權限不足；保留實際可見範圍 |
| 5. 已證實過度授權但輔助查詢受阻 | 保留充分 not-met 與缺口，不把全部壓成 blocked | L／R 原始權限證據與可見性限制；指定交叉組合可 F |
| 6. 本連線已加密但強制 TLS／客戶端驗證／其他連線未證實 | 各主張分開，缺證據 indeterminate，充分違反 not-met；不外推全部連線 | L TLS 正反例；R 指定客戶端與政策要求的拒絕證據，範圍明列 |
| 7. RDS 要求值、pending、生效值或憑證證據不同 | 區分設定階段與證據語意，未解決相關矛盾 indeterminate | 三引擎 R 真實 pending 到生效鏈及憑證更新鏈；指定矛盾可 F |
| 8. 長交易／鎖等待、高負載、空間不足或複製超標 | 各分支停止受影響交接／交人安全停止，不自動 kill、延長或改門檻 | 三引擎 L 受控鎖／長交易案例；其餘超標及精確預算截斷用 F |
| 9. 版本／操作不適用、ALGORITHM／LOCK 不滿足或需外部 OSC | 各分支不靜默降級／換工具；保留條件並交人／專家 | L 正常 DDL 固定版本／操作／儲存引擎條件；不適用與外部 OSC 分支用 F |
| 10. DDL 失敗／逾時／斷線但部分提交或結果未知 | 先確認實際狀態，不盲目重試或宣稱整批 rollback；區分交易邊界 | MySQL／MariaDB L 各自真實部分完成；未知結果及危險重試分支可 F |
| 11. PG concurrent index 失敗留 INVALID 或其他殘留 | 不把失敗當未變更，記錄有效性、影響及人工清理批准 | PG L 真實 INVALID、人工清理與驗證；其他殘留分支可 F |
| 12. 無通用 rollback、僅備份存在或不可復原風險未接受 | 各分支不得報就緒；沿用復原證據／合法風險接受及強制要求 | L 正常 DDL 復原方案與適用證據，可引用合格 B1 證據；不為測試製造不可復原事故 |
| 13. 權限變更造成應用／管理失敗或既有／新連線不同 | 分開判授權效果與存取，揭露部分生效，不自建帳號或繞過權限 | L 權限前後允許／拒絕與適用連線證據；真實管理者鎖出／應用故障不要求重現 |
| 14. TLS 更新但不信任、重連失敗或仍接受禁用連線 | 各失敗分支分項判，不由設定成功／舊連線正常報輪替完成 | L 安全拒絕；三引擎 R 憑證更新與新連線／重連成功鏈；輪替事故可 F |
| 15. 批准拒絕／過期／撤回／資格不明、改案或超範圍重試 | 各停止點分開；已開始交人依計畫處理，停止不等於 rollback | 新演練保留批准及人工執行；不要求危險撤回操作 |
| 16. 命令成功但 schema／資料／應用／複製驗證失敗或不足 | 各必要子主張分別 not-met／indeterminate，保留混合結果 | L DDL／權限及 R 憑證事件保留相應必要驗證；指定失敗／不足可 F |
| 17. capability 非 available、contract 不支援、CALL 拒絕或平台前置缺失 | 非 available 阻擋受影響步驟，contract 不支援停整個流程；CALL／AWS／IAM 按既定規則，不繞 gate | L／R 留存必要 capability、實際工具版本與權限；不支援／缺失分支 F |
| 18. 歷史成功但現況變動、證據過時／不可得或保存失敗 | 保留歷史與當前適用性缺口；無合格替代時相關主張 indeterminate | 抵用歷史證據逐項審查且可復核，不免當前 F |
| 19. 清理／復原失敗或人工探測需額外權限／寫入 | 分開驗殘留、接手人與批准交接，不虛稱收尾或以驗證擴權 | 實證保存實際收尾／殘留交接；PG INVALID 有人工清理驗證；故意清理失敗可 F |

共同交叉案例包括混合主張、充分 not-met 但輔助查詢受阻、相關矛盾與受阻並存、必要證據保存失敗有／無合格替代，以及 blacklist／列數保護／原生權限造成不完整可見。

沿用 B3／ADR-0046 優先序：充分且無相關矛盾先判 met／not-met；否則相關矛盾 indeterminate，再判必要步驟受阻 blocked，其餘不足 indeterminate。CALL 拒絕與缺 AWS CLI／唯讀 IAM 等特定缺口按既定政策，不一律改判 blocked。整體 workflow 可有混合結果，不另創第五種主張狀態。

### 5. 行為重跑與判讀

F 必須執行真正 Role Skill，不只測旁邊的判斷函式或由人工閱讀示例。合成來源、時間、基準明示；受控工具替身攔截外部效果並記錄所有嘗試呼叫。

每個必要案例固定可重建 Skill 內容、fixture／預期行為、工具契約、模型識別與可控制設定、runner 版本，以全新 session **至少三次，全部符合才 PASS**。無法固定的模型服務部分揭露；三次通過不代表確定性保證。

逐次保存輸入、預期／實際輸出、工具順序／參數／回應／攔截與判讀理由，語意判讀須可人類復核。禁止操作嘗試、漏停、繞 gate、無證據成功聲明及其他未達預期均 FAIL，即使外部效果被攔截也不例外。不多數決、不挑成功重跑；修正後新候選的受影響案例重跑至少三次，原失敗保留。

### 6. 人工、歷史與受控證據

證據連結可重建候選內容、案例、對象／環境及完整版本、帳號／角色範圍、政策／資料／應用基準、時間、來源、批准、實際操作、前後觀察、必要驗證，以及收尾或殘留／接手人。可取得的來源 ID、文件／檔案內容與雜湊用於追溯；雜湊不替代可重建內容，也不證明真實性或批准。

歷史證據逐項核對版本、部署、操作、設定、權限、客戶端、基準及目前用途的適用性，只抵用相應實證；不免當前候選 Skill 行為測試。歷史技術結論與批准合規分開，不因結果成功補造當時批准，也不把過去成功自動升格為目前符合。

公開摘要去敏。敏感原始證據使用可被授權審查者復核的受控引用，不裁掉影響判定的事實；密碼、認證字串、密碼雜湊及私鑰不進測試紀錄。必要證據不可取得／保存失敗且無合格替代時，保留對應缺口與既定主張結果。

新演練的隔離、人工批准、執行、停止、復原與清理均沿用 B3。一次有效批准可以明確涵蓋多步，每步核對適用性；批准不自動觸發操作。清理失敗記殘留、原因、接手人與解除條件，不虛稱收尾，也不覆寫已成立的歷史技術結論。

### 7. 缺口、變動與工具邊界

缺環境、權限、人工操作、客戶端、應用或其他必要證據時，列明受影響案例／路徑／主張、已有證據、缺項、原因、解除條件與接手人。缺口登記不是 PASS，也不能藉豁免升成完整驗收。

Skill、工具契約、模型／runner、引擎版本、權限、TLS、部署、客戶端或基準變動時，先記錄影響分析與可沿用證據的理由，再補驗受影響部分；無法界定則相關範圍維持未驗收。證據時效依已確認政策，不設通用天數。歷史結論與失敗不覆寫，當前聲明另更新。

沿用[各工作流程的 capability 需求與 Tool 缺口定案](https://github.com/CarlLee1983/dbcli/issues/255#issuecomment-6259411027)。按實際操作檢查必要 capability 與 contract；available 不證明握手、原生權限、完整可見性或批准。`connection.tls` 是已核准但待交付的 Tool 缺口，本票不宣稱已實作；TLS 必要步驟缺能力／明確設定時停止受影響蒐證，不靠 ambient 行為、明文或停用驗證補過。既有 TLS Tool 正反例要求不因本票引用而縮減。

CALL 拒絕政策維持，不自動換原生客戶端或 AWS API；原計畫內 RDS 唯讀觀察可照計畫使用。不得放寬 agent mode、blacklist、write gate、production 選擇或原生權限以湊齊證據。新的必要操作若揭露可重現原子 Tool 問題，附必要行為、現況及可觀察驗收另行立案；本票不新增推測性 capability。
