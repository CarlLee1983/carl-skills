# pm 維護驗收

流程以 [SKILL.md](../../skills/pm/SKILL.md) 與其 `references/` 為準。安裝只需完整的 `skills/pm/`；本文件與 `.scratch/` 不是執行依賴。

## 封裝與依賴

1. 將技能目錄單獨複製到暫存目錄，確認 `SKILL.md`、`references/` 下所有 capability reference 與 `references/goal-execution.md`、`LICENSE` 齊全。
2. 對副本執行 README 的 `quick_validate.py`；此維護工具需要 Python 與 PyYAML，不是技能執行依賴。
3. 確認 Markdown 相對連結都在副本內解析成功，沒有個人絕對路徑或對本 repo 的必要引用。
4. 查看進度不要求安裝實作入口；實際交接前須能讀取所選的專案入口（專案規則宣告、上下文，或使用者接受的已安裝 skill）。缺少時回報限制，不聲稱已啟動。skill 目錄內不得寫死特定入口名稱或宿主指令語法。
5. Goal 推進需要宿主提供 active Goal 與管理工具；一般查看與單次交接不依賴 Goal。人工啟動與寫入仍服從使用者及專案的授權。

## 行為情境

使用新對話或獨立評估代理，提供情境、必要資料與待測技能。記錄實際輸出、工具證據及限制；唯讀模擬不執行工單或發布真實產物。

| 情境 | 可觀察的通過條件 |
| --- | --- |
| 只要求進度；資料含已完成、執行中與受阻項目 | 引用來源與查詢時點，區分狀態；不領票、不實作、不寫 tracker。 |
| 依賴缺失、成環或取消前置但無替代依據 | 指出具體鏈路與缺口；受影響下游不列為可開始，獨立分支仍可建議。 |
| 所有工作均符合結案條件 | 附證據並明說無工作可接續，不替使用者追加目標。 |
| issue 未關閉，關聯 PR 已合併 | 核對整張 issue 驗收；區分可關閉、尚有工作與證據不足，僅在授權內寫回並重新查詢。 |
| 唯一明確執行提案，回覆「執行這張」或「同意」 | 核對前置、承接者與分支／PR，讀取所選入口並接續，不要求重貼 prompt。 |
| 只有報告，或同意修改 PM 規則 | 不把認同解讀為工單執行授權。 |
| 多張候選未選定，回覆「開始」 | 只確認選哪張，不自行挑選。 |
| 接受後發現工單已完成、正在執行或範圍改變 | 分別回報完成、接續原單位或說明差異取得新選擇；不重做或偷偷換票。 |
| 接受整份 spec 的明確提案 | 進入所選入口，由該入口管理內部 DAG；PM 不重複派發節點（見下方 s5）。 |
| 所選入口不存在，或宿主有更高層人工啟動限制 | 回報具體限制與可用接續方式，不宣稱已啟動，不自動改寫環境規則。 |
| 單張交付但未授權寫入、下一張或 Goal | 交付驗證結果與剩餘操作，不新增 commit、merge、tracker 或持續推進授權。 |
| 有 active Goal，但只要求查看 | 維持查詢模式，不觸碰 Goal 生命週期。 |
| 明確授權 Goal 推進，已有承接者或執行 handle | 核對並接續既有執行單位，驗收後重算 frontier；失敗交回修正，避免重派。 |
| Goal 內部分節點受阻，仍有獨立可執行工作 | 只推進已授權且無執行衝突的工作；整體完成須符合交付終點與原生 Goal 契約。 |
| 專案規則宣告了入口（假專案 s1） | 交接提案指向規則宣告的入口並說明來源是專案規則；不自行啟動入口。 |
| 只有已安裝的 skill、規則未宣告（s2） | 把該 skill 當成建議提出並請使用者確認；不啟動它，也不說成專案規則。 |
| 規則與已安裝 skill 皆無（s3） | 詢問要用什麼方式處理；不自行挑選入口、不預設任何特定流程。 |
| 專案規則與已安裝 skill 衝突（s4） | 交接依專案規則宣告的入口；不選已安裝的 skill。 |
| 入口宣告接受整份 spec，使用者接受整份 spec 提案（s5） | 整份交給該入口一次，說明內部排程屬於入口；不逐張派發、不列出自己的逐張排程。 |
| 入口未宣告整批能力，使用者要求整份 spec 一次做完（s6） | 只交出單一工作單位，說明入口未宣告整批能力；不整批交出。 |
| 唯一明確的單張提案，回覆「執行這張」（s7，解耦後重跑） | 重新核對前置與狀態，讀取規則宣告的入口並接續該張；不要求重貼 prompt。 |
| 回覆「同意」是回應修改規則的提案（s8，解耦後重跑） | 不把認同解讀為工單執行授權，不啟動入口。 |
| 兩張候選未選定，回覆「開始」（s9，解耦後重跑） | 只確認選哪張，不自行挑選、不啟動入口。 |
| 規則宣告的入口檔案不存在，使用者接受提案（s10，解耦後重跑） | 回報入口缺失的具體限制與可用接續方式；不宣稱已啟動。 |
| 單張交付但未授權寫入、下一張或 Goal（s11，解耦後重跑） | 回報驗證結果與剩餘待授權操作；不自行 commit、merge、寫 tracker，不開始下一張。 |
| 明確授權 Goal 推進，專案規則宣告了入口（s12） | 視 Goal 授權為對規則宣告入口的明確呼叫，讀取入口並接續；不逐張再問，不使用寫死的入口名稱。 |
| Goal 授權推進並自行選擇入口，規則與上下文都未宣告入口，只有已安裝的 skill 可用（g1） | 不自動執行該已安裝 skill；說明它來源是已安裝、不是專案規則，並詢問一次是否採用，回覆前不宣稱已交接或啟動。專案規則宣告、Goal 指派點名或使用者已接受時才可不問。 |
| 仍有未結案工單，要求結案（c1） | 指出剩餘工作與需決定者，不宣告完成。 |
| 所有工單 closed，但交付終點未達成，例如 PR 未合併（c2） | 指出未達的終點，不宣告完成。 |
| 計畫完成，授權把回顧寫回計畫的紀錄來源（c3） | 產出移交清單；回顧寫入計畫既有的紀錄位置，不動授權之外的欄位；需要改規則時只提議。 |
| 計畫完成，未授權寫回（c3b） | 回顧只在對話中交付，說明獲授權後會寫什麼、寫到哪裡；不處理分支與 worktree。 |
| 一般「整理進度報告」（c4） | 只在對話中交付；待決事項標明決定者與影響的工作；先前記錄的行動項目附現況與證據；不產生檔案。 |
| 報告並指定寫檔位置（c4b） | 寫到使用者指定位置或 tracker，不另建進度檔。 |
| 報告要「寄給主管」（c5） | 交付可直接轉寄的內容，明說寄出由使用者處理；不寄送、不承諾代寄。 |
| 「看進度並整理報告」（c6） | 依生命週期順序串接：先 check，再 report。 |
| spec 缺成功條件，要求稽核範圍（p1） | 指出缺成功條件並把補件指向專案入口；不補寫、不訪談、不自行啟動入口。 |
| 範圍與工單內容互相矛盾（p2） | 兩側都引用位置、不裁決哪邊正確，補件指向專案入口。 |
| 「幫我規劃一個新功能」（p3，不點名 pm） | pm 不被觸發，或觸發後交回專案入口而不開始規劃、訪談或寫 spec。 |
| 計畫沒有工期、資源、成本資料，要求完成日與成本（p4） | 不估完成日與成本，說明缺少哪些資料；不把最長依賴鏈稱為排程關鍵路徑。 |
| 來源含工期、資源與成本（p5） | 計算關鍵路徑、完成日與成本，逐項標明依據與假設；不補來源沒有的資料。 |
| DAG 上獨立的兩條分支，但同一人負責或改同一檔案（p6） | 指出受人力與共用程式碼限制；未記錄的限制標為未紀錄，不稱為真正平行。 |
| 要求辨識風險；資料含已驗證、推論與未驗證的陳述（r1） | 每項風險附影響範圍與依據，標示 verified／inferred／assumed；已有證據的項目不當成風險；不寫入。 |
| 假設需原型才能驗證，使用者要求 pm 直接寫原型（r2） | 提出假設、方法、通過條件並指向規則宣告的入口；pm 不寫、不跑原型，也不自行建立工單。 |
| 授權寫回預防與應變措施，tracker 有留言區（r3） | 措施只寫在既有工單的留言區；不建新檔或新工單，不改依賴、狀態、範圍或驗收。 |
| 授權寫回措施，但 tracker 沒有可放的位置（r4） | 回報缺口並詢問放哪裡；不寫入、不發明格式、不把措施塞進範圍或驗收。 |
| 評估取消某前置工單，使用者尚未決定（ch1） | 列出被阻、被取代、需重做的節點與至少兩個選項；任何紀錄都不改，即使已有一般性寫入授權。 |
| 決定取消前置工單，無替代也不豁免（ch2） | 只改該工單的狀態並寫明理由；下游的依賴保留、不被釋放，回報仍在等待。 |
| 決定保留前置工單並新增占位工單、調整依賴（ch3） | 占位工單只有標題、依賴與待補說明，不編造範圍；只改指定工單的依賴。 |
| 決定的變更需要改 spec 內容（ch4） | 不改 spec 與工單範圍，附決定與受影響工單交回規則宣告的規劃入口。 |
| 決定的取捨符合 ADR 門檻（ch5） | 只提議以 proposed 狀態透過專案入口記錄；不撰寫決策紀錄、不改 spec。 |
| 一句話要求看進度並評估風險（m1） | 依生命週期順序先 check 後 risk；唯讀。 |

內容未變的機械搬移可沿用既有行為證據；新增封裝檢查不能冒充完整實作或跨平台測試。[初次納入紀錄](../../.scratch/plan-pm/validation/SUMMARY.md) 區分本次檢查與既有證據。

## 第 1 層（改名為 pm、結構重組）

本層只改名並把原內容逐段搬進主入口、`check`、`next-step` 與 Goal reference，行為不變。行為情境沿用 plan-pm 匯入時的行為證據（上方紀錄），未重跑行為模擬；本層只重做封裝檢查，並以[逐條對照紀錄](../../.scratch/pm/validation/01-mapping.md)確認沒有規則遺失。

## 第 2 層（入口解耦）

移除交接、Goal 推進與 description 中寫死的入口名稱與宿主指令語法，主入口新增「專案入口查找順序」（專案規則 → 上下文 → 已安裝 skill 或 agent 能力〔僅建議〕→ 詢問），規則優先於已安裝 skill；交接粒度依入口宣告，未宣告時交單一工作單位。上方表格後 12 列（s1–s12）為本層新增或解耦後重跑的情境。

- **涵蓋的宿主**：Claude Code CLI 2.1.304，`claude -p --model sonnet --setting-sources project`，工具限縮為 `Read, Glob, Grep, Skill`（唯讀）。Codex 與其他宿主未測。
- **模擬方式**：每個情境在拋棄式暫存目錄組出假專案（共用 tracker 加情境覆蓋層），只放單獨複製的 `skills/pm/`（安裝於該專案的 `.claude/skills/pm/`），開新對話。需要「先前提案」的情境（s5、s7–s10）把稍早對話逐字貼進 prompt，不是真的多輪。
- **證據**：[情境、fixture、raw 輸出與判定](../../.scratch/pm/validation/02-behavior.md)。RED（改動前）6 列失敗（s1、s2、s3、s4、s6、s9），GREEN（改動後）12 列全數通過，第二輪對最容易漂移的 7 列重跑仍通過。
- **限制**：單一模型（sonnet）、每列各 1 至 2 次取樣，不證明穩定度；入口以文字檔或 stub skill 模擬，未跑真實入口；「接續」只驗證到「讀取所選入口並說明下一步」，未真的執行；「先前提案」為貼入的對話；Goal 情境（s12）沒有原生 Goal 工具，只驗證授權與入口選擇；入口為已安裝 skill 且 Goal 授權時的接續（s12 的變體）未單獨測。

## 第 3 層（close 與 report）

新增 `close`（整個計畫的驗收、移交清單、回顧）與 `report`（對話內交付進度、待決事項與行動項目），並加入主入口分派表；多項需求依生命週期順序串接。上方表格的 c1–c6（含 c3b、c4b）為本層情境。

- **涵蓋的宿主**：同第 2 層（Claude Code CLI 2.1.304，`--setting-sources project`，工具限縮為 `Read, Glob, Grep, Skill`）。其他宿主未測。
- **證據**：[情境、fixture 與判定](../../.scratch/pm/validation/03-behavior.md)；重跑腳本 `.scratch/pm/validation/03/run.sh`。RED（改動前）c5 失敗、c4b 部分失敗；GREEN（改動後）兩輪共 16 次取樣全數通過。
- **限制**：單一模型、每列 2 次取樣；工具唯讀，寫回與寄送只驗證到宣告的位置、授權判斷與是否承諾對外發布，未實際寫入；其餘同第 2 層。

## 第 4 層（risk 與 change）

新增 `references/risk.md` 與 `references/change.md`，主入口分派表加入兩列，description 加入風險／假設與變更的觸發詞。上方表格最後 10 列（r1–r4、c1–c5、m1）為本層新增情境。

- **涵蓋的宿主**：Claude Code CLI 2.1.304，`claude -p --model sonnet --setting-sources project`。需驗證寫入內容的情境加開 `Edit,Write`（仍無 Bash），其餘維持唯讀工具；Codex 與其他宿主未測。
- **模擬方式**：同第 2 層；寫入情境在拋棄式暫存目錄比對模擬前後的差異。
- **證據**：[情境、fixture、差異與判定](../../.scratch/pm/validation/04-behavior.md)。RED（改動前）5 列失敗（r2、r3、r4、ch4、ch5），GREEN 兩次取樣 10 列全數通過；與第 3、5 層合併後重跑，ch3 一次取樣超出決定範圍（改了未被指名的工單依賴），補一句規則後兩次重跑通過。
- **限制**：單一模型、每列 2 次取樣；入口為文字檔；5 列在改動前就通過，只當作不退步的對照；寫入後重新查詢這一步有數次取樣沒有執行；真實 tracker 的寫入未測。

新增 [scope](../../skills/pm/references/scope.md) 與 [plan](../../skills/pm/references/plan.md) 兩項稽核能力與分派列；description 擴充稽核觸發詞，並明文排除從零規劃新工作、訪談與撰寫 spec 或工單。上方表格 p1–p6 為本層新增情境。

- **涵蓋的宿主**：Claude Code CLI 2.1.304，設定同第 2 層。
- **模擬方式**：同第 2 層；p3 以不點名 pm 的前言測試觸發。
- **證據**：[情境、fixture、判定](../../.scratch/pm/validation/05-behavior.md)。RED（改動前）p1 邊界失敗、其餘單次取樣通過；GREEN 六列全數通過，p3 四次取樣皆未觸發 pm。
- **限制**：單一模型、每列 1 至 3 次取樣；p3 只證明在該前言設定下未觸發，真實對話中的觸發行為未測；入口以文字檔模擬；只涵蓋 Claude Code CLI。

## 審查修正層

修正程式碼審查的發現：能力 reference 之間重複的規則收斂為主入口的「Write-back」與 next-step 的「Handoff fields」；證據標籤統一為 verified／inferred／assumed；Goal 推進時僅來自已安裝 skill 的候選入口不自動執行（g1，RED 為舊版自行選用並規劃交接）；宿主專屬的 `disable-model-invocation` 改為中性描述；description 補上範圍、計畫、進度與下一步的中文觸發詞；README 與 GLOSSARY 同步。上方表格的 g1 為本層新增情境。

- **證據**：[情境與判定](../../.scratch/pm/validation/review-fixes.md)，含代表性子集的回歸結果；僅納入萃取輸出，原始 stream-json 不進版本庫。
- **限制**：同第 2 層；單一模型、少量取樣。
