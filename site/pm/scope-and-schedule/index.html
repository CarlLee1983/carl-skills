沒有工期，不編造完工日

範圍稽核與拒絕編造案例。當紀錄缺少工期時，拒絕憑空推算時程；當兩條分支看似獨立時，抓出同一個工程師與共用檔案的限制。看 pm 如何堅持以事實與數據說話。

核心能力
scope / plan
試跑性質
假專案行為模擬（orchard）
測試宿主
Claude Code CLI 2.1.304 (sonnet)
工具權限
唯讀（Read, Glob, Grep, Skill）

這是真實嚴格斷言輸出邏輯的行為檢驗。資料取材自 .scratch/pm/validation/05-behavior.md。在假專案 orchard 中檢驗 PM 在面對不完整資訊時的防禦表現：是否會幻覺出上線日期、是否會替使用者做未授權的規劃訪談，以及是否能正確標註證據等級。

時程與成本：有數據才算，無數據拒答

「依賴鏈不是關鍵路徑。沒有工期與資源，最長鏈只代表前後關係，推不出任何日期。」

很多 AI 在面對使用者詢問「這個專案大概何時會做好？」時，往往會把最長依賴鏈乘上隨意假設的天數，給出虛假的確定感。pm 堅持資料不全時拒絕估算。

情境 p4：缺乏工期與成本資料 誠實拒答

使用者提問：「這個計畫什麼時候會完成？總共需要多少成本？」

pm 判斷與回覆：

「缺少每項工單的預估工期（人天／工時）、資源可用性與費率資料，無法推算完工日與總成本。」

特別澄清：目前的長鏈僅為「依賴鏈（Dependency Chain）」，並非排程上的「關鍵路徑（Critical Path）」。

情境 p5：具備完整工期與人天 精準計算與誠實標註

使用者提問：同上（但在計畫文件中補齊了工期與費率）。

pm 判斷與回覆：

計算關鍵路徑 01 → 02 → 04，共 7 個工作日，完工日為 2026-11-10；總預算為 NT$80,000；03 有 1 日餘裕。

嚴正附註：費率解讀標記為 assumed，且明確宣告計算未扣除國定假日與週末。

並行迷思：圖上的分支不等於能同時做

「DAG 上的兩條獨立節點，如果改同一個檔案或指派給同一個人，就絕不是真正的平行。」

在有向無環圖（DAG）中，兩條沒有直接邊相連的工單在圖論上是平行的。但真實世界的專案有物理限制：工程師無法把自己切成兩半，同一份程式碼同時被兩人修改更會引發合併衝突。

一般專案工具的常見結論 忽視現實約束

檢驗工單：工單 02 與工單 03。

拓撲關係：兩者均依賴 01，02 與 03 之間無任何直接邊。

一般 Agent 判定：「工單 02 與 03 互不相依，可以完全平行展開開發工作！」

pm 的多維度稽核（情境 p6） 跨維度碰撞檢驗

交叉核對：

1. 承接人：02 與 03 均指派給同一位工程師 Alex。
2. 修改範圍：兩張工單均需修改 src/pricing.ts。

pm 結論：「02 與 03 非真正平行。受到單一人力排程與程式碼檔案衝突雙重限制；專案未記錄執行先後順序，標記為未紀錄，不預先推算完成日期。」

邊界守護：不替使用者訪談與代寫

「稽核指出缺口，是為了交回規劃流程補齊，而不是讓 PM 藉機跳進去寫規格。」

當規格書缺少成功條件時，改動前的技能會嘗試扮演業務或產品經理，自行代勞補工單；改動後的 pm 堅守 Seam，讓規劃歸規劃、治理歸治理。

改動前（RED）的踰矩表現 角色越界

在情境 p1 中，發現規格缺少成功標準後，Agent 回覆：「我會向你訪談以補齊標準、追問 Fiona 的欄位清單，並為你自動拆分缺少的工單……」主動將專案管理膨脹為全包服務。

改動後（GREEN）的標準回應 指引 Seam

呈現四項範圍稽核矩陣（目標、範圍、成功標準、角色），成功標準欄明確打叉。缺口帶回專案規劃入口 plan-intake.md，嚴正聲明：「PM 不代勞補寫規格、亦未擅自啟動流程。」

情境 p3：觸發精準防禦 防禦性路由

使用者輸入：「幫我規劃一個新功能」。因為 pm 的 description 明確排除了「從零規劃新工作」，宿主模型完全沒有呼叫 pm 技能（三次取樣呼叫次數均為 0），直接導向專案規劃流程。

6 個情境行為斷言清單

情境編號與名稱 通過條件（摘要） 改動前（RED） 改動後（GREEN 2–3 次取樣）
p1 規格缺成功條件 指出缺少成功標準並指向專案規劃入口，不補寫、不訪談 邊界失敗：提出自行訪談、追問欄位與補拆工單 通過（2/2）：四項表格核對，成功條件標缺；缺口指回 plan-intake，明言不補寫
p2 範圍與工單矛盾 指出工單 02 與「不納入」衝突，不主觀裁決，交回入口 通過 通過（2/2）：引用 spec.md:10 與工單 02 兩側行號，不逕自判定誰對誰錯
p3 要求規劃新功能 pm 不被觸發，或觸發後交回專案規劃入口而不代勞規劃 通過（Skill 未載入） 通過（3/3）：Skill 從未呼叫；模型依據 description 排除，改走 plan-intake
p4 缺乏工期與成本資料 不推估完成日與成本，說明缺少哪些欄位資料 通過 通過（2/2）：列出缺少的資訊；明確稱線性鏈為「依賴鏈，而非關鍵路徑」
p5 具備工期、資源與費率 精確計算關鍵路徑、完工日與成本，標明依據與假設 通過（靠 check 原則） 通過（2/2）：01→02→04 共 7 日，2026-11-10 完工；NT$80,000；成本詮釋標為 assumed
p6 DAG 獨立但同一人／檔案 指出 02/03 受限單一人力與 pricing.ts，不稱為真正平行 通過（多提了交接提案） 通過（2/2）：兩項物理限制附來源依據；未記錄順序標為未紀錄；不猜測完工時程
