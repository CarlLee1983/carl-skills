生命週期八大能力

一個指令若橫跨多項需求（例如「看進度並整理報告」），pm 依生命週期順序串接：前面建立的事實，後面直接引用。

  1. Scope

    範圍稽核。開工前核對目標、範圍、成功標準與角色邊界是否已具備且一致。缺少成功條件時指出缺口並交回專案規劃入口，不自行代勞訪談或補寫工單。

  2. Plan

    計畫稽核與時程。盤點里程碑、相依關係與真實並行限制。缺少工期與成本資料時，拒絕憑空推算完成日；有完整資料時才計算關鍵路徑，並誠實標註未計假日的假設。

  3. Check

    進度與依賴盤點（預設意圖）。從 tracker 建立 DAG，分出已完成、進行中、就緒、等待與資訊不足；主動核對未關閉工單與已合併 PR 的對應，不讓結案漏勾。

  4. Next-step

    推薦與單次交接。列出就緒前緣並提出單一交接提案。依照「專案規則 → 上下文 → 已安裝技能（僅建議）→ 詢問」查找入口，使用者回覆「執行這張」才正式接續。

  5. Risk

    風險與假設識別。從紀錄來源找出隱含風險與未驗證假設，標註影響範圍與證據層級。提出交給專案入口的原型或研究建議，pm 自己只做唯讀查證、不跑實驗。

  6. Change

    變更衝擊評估。取消、置換或插入工單時計算對 DAG 的衝擊。取消前置工單絕不偷偷釋放下游；決策涉及架構時提議記錄 ADR，絕不私自改動 spec。

  7. Report

    進度報告交付。預設直接在對話中交付現況、待決事項（含決定者與受影響工單）與行動項目；只有使用者指定時才寫入檔案或 tracker，絕不自行對外發信或發布。

  8. Close

    全計畫結案與移交。只有在全數工單 closed 且交付終點（如 PR 已合併）達成時才結案。產出移交清單，經驗回顧寫回計畫原有的紀錄位置，不動授權之外的欄位。

守住邊界的三條鐵律

很多 AI 專案管理工具最後變成「第二本帳本」，或是為了討好使用者而擅自做決定。pm 藉由三條不可逾越的架構鐵律，保證任何操作都在授權與既有紀錄之內。

1. 唯讀優先與零污染

所有查詢與分析預設唯讀。寫回時只寫既有 tracker 或指定位置，絕不發明進度檔、狀態機或私有格式。tracker 若沒有對應欄位，主動回報缺口並詢問放置位置，絕不把雜項文字硬塞入驗收標準。

2. 嚴格的三級證據分級

結論必須標明依據：
verified 引用 PR、CI、量測或查詢紀錄。
inferred 從非直接量測資料推導出的邏輯。
assumed 未經量測證實的設定（如人天成本）。
絕不把假設升級為事實。

3. 依序查找專案入口

交接與補件不預設任何特定工作流，查找順序為：
1. 專案規則（AGENTS.md、CLAUDE.md）
2. 上下文（對話提及或 tracker 指定）
3. 已安裝技能（僅作建議，說明非專案規則）
4. 停下詢問（都無時不自行決定）
專案規則與已安裝技能衝突時，專案規則必勝。

三個案例

  1. 入口解耦與授權判定 規則先於宿主預設、認同改規則不等於執行工單授權、唯一的單次交接提案。從 12 個行為情境看它如何釐清授權邊界。 情境 s1–s12
  2. 變更衝擊與依賴保護 前置工單取消時下游不被偷偷釋放、預防措施只寫入既有留言區、提議 ADR 而不私自竄改 spec。變更與風險的真實防禦。 情境 ch1–ch5, r1–r4
  3. 範圍稽核與拒絕編造 缺少成功條件時交回規劃入口、缺少工期資料拒絕猜測完工日、抓出同一人與共用檔案的偽平行鏈路。 情境 p1–p6

越權失控與邊界守護

未經規範的 Agent 常把「規劃」「實作」與「治理」混為一談，造成帳本與現實脫節。pm 透過清晰的邊界切割，讓專案管理保持純粹的秩序。
