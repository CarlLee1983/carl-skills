照著生成圖做預約網站

主題起手加目標稿：使用者手上有一張 AI 生成的預約網站圖，說「想做成這樣」。技能不照圖畫，先逐區審查，把每一處判成照做、改做法、刪除或待產品決定，再做原型和原圖並排給使用者看。

這是腳本試跑。使用者每句回覆都取自腳本，沒有真人。店名 PawLux（暫名）、服務、價格、時段與預約編號都是虛構的示例資料。所謂的 AI 生成圖，是用本機 HTML 渲染出來的 AI 風格圖，刻意埋了拼錯字、虛構宣稱這類瑕疵，用來檢查技能抓不抓得到，不是真的 AI 作品。

這張圖是目標稿

做一個寵物美容店的預約網站，我用 AI 生成了這張圖，想做成這樣。

專案只有後端 API（服務清單、某日時段、建立預約、取消預約），沒有介面、品牌、logo 或設計系統，店名也沒定，所以進入模式是主題起手。

圖的種類判成目標稿，不是參考網站。依據是「想做成這樣」，而且這是為使用者生成的圖，不是別家公司的真實產品。目標稿是要做出來的提案，所以先審查再動手；圖上的名稱與 logo 都先當佔位。

審查先列出圖做對的地方，這些會保留：暖紫到珊瑚的色溫、大而友善的主標、醒目的橘色「立即預約」、第一屏就看得到今天還能約的時段、大圓角柔和的卡片。

圖只畫了首頁第一屏。選時段、填資料、確認、完成這些步驟圖上沒有，技能依 API 用同一套視覺補上，並標明是新增步驟。

逐區審查

圖分成八區：頁首、主標與副文、行動按鈕、心情指數與時段卡、美容師位置卡、評價卡、背景與構圖、頁尾。審查共 25 項發現（F1 到 F25）：照做 1、改做法 15、刪除 5、待產品決定 2，另有 2 項被其他卡片蓋住、不臆測。

下表挑出有代表性的幾項。「待產品決定」不是設計問題：會員登入與美容師即時位置都需要專案沒有的能力，要不要做是產品範圍。F23 的「Partnered with airbnb」是別家公司的名稱與 logo，也是不實的合作宣稱，一律移除。

審查是肉眼看靜態圖。焦點、溢出這類基線項目從圖上看不出來，留到原型截圖時才檢查。

只問圖回答不了的題

圖已經回答了不少事，所以訪談只問它回答不了的：誰在用、淺色還是深色、圖上哪些是真的想要。每題有編號、建議答案與理由，使用者可以只回題號。

審查的取捨都照你的建議。Q1：讀者是附近的飼主，主要行動是線上預約。Q2、Q3、Q4：只做繁中、淺色、手機優先。Q5：圖上我真正想要的是溫暖親近的氣氛，以及第一屏就能選服務。Q6：對。其他題目照你的建議。

原型和原圖並排

v1 是一個離線 HTML：第一屏就能選服務，往下走完選時段、填資料、確認、完成，載入、無時段、載入失敗、時段被約走、表單錯誤都做成看得到的狀態。技能把原圖和 v1 第一屏放成同為 1440×1000 並排，每個差異都標上它對應的發現編號。

右側那疊玻璃卡片變成一張預約卡（F13、F17）；橘色只留給卡裡的「下一步」（F10、F11）；主標改成繁中，副文只說 API 做得到的事，也就是免註冊、簡訊通知、點簡訊連結取消（F6 到 F9）；深色底改成淺色，紫到珊瑚的色溫留在淡漸層與品牌紫（F20）。

原型裡沒有的也寫明了：刪除的有 AI 心情指數、虛構評價、airbnb 字樣與裝飾用 emoji；待產品決定而沒放進去的是會員與登入、美容師即時位置。

技能看 v1 截圖時抓到並修了五處：390 寬第 2 步整頁橫向捲動、步驟條在手機上逐字換行、體型選項內距被蓋掉、輸入框邊框對比只有 2.19:1（改為 3.81:1），以及「無時段」文案原本寫「約滿」，但 API 只回空陣列、分不出約滿還是公休，改成「沒有可預約的時段」。

它還自己走查時量到：390 寬選了第三項以後，「下一步」按鈕在 985px，視窗只有 844px。技能把這點標成「我自己的檢查，不是使用者試用」，沒有先改，請使用者試用時確認。

一句回饋，改一版

試用任務是「幫你家狗約下週二下午做全身美容，走到看見預約編號為止」，並請使用者分開回答喜歡哪裡、哪一步卡住。

我試用了。喜歡那個溫暖的感覺。不過做預約的時候，選完服務我不知道下一步要去哪裡。

這句腳本沒有為了配合而調整：v1 在 390 寬確實有這個問題，程式量測也記錄在驗證檔裡。喜歡的部分不動；卡住的部分，原因和技能先前量到的一致，按鈕在畫面外，選了也看不出有什麼變化。

v2 只改第 1 步的行動列：手機寬度（767px 以下）且已選服務時，它固定在畫面底部，上面一行寫「已選　服務名稱　價格」，下面是橘色的「下一步：選時段」。沒選時維持原樣，桌機版不變，1440 寬選完服務按鈕本來就在畫面內（y=840，視窗 1000）。改後量到按鈕在 780px，落在畫面內。

v2 重做了整套主要路徑的程式檢查，但使用者沒有重新試用 v2。「不知道下一步」有沒有真的解決，目前只有量測與截圖支持。

定稿，交接清單

定稿。

定稿的是 v2：結構 A（左主標、右預約卡，第一屏選服務）加視覺處理 1（從原圖延伸的淺色版，暖米白底、深紫字、品牌紫標示選取、橘色只給每一步唯一的主要行動）。結構與視覺分開記為已接受。生產實作沒有授權，設計停在交接。

交接寫了畫面、四個步驟的操作、六種狀態與復原方式、可重用元件、資料來源與 9 條驗收情境，並把目標稿上不要照做的部分列清楚，避免實作時照圖補回。

驗證到哪裡

用 Playwright 1.64.1（Chromium headless，macOS）開啟原型、截圖並跑程式化檢查。下面摘自 SESSION 與驗證檔。

做過的檢查

  • 主要路徑程式檢查：v1 與 v2 各 32 項，全部通過。涵蓋 390 與 1440 寬走完選服務到完成、鍵盤路徑、時段載入失敗與被約走，以及沒有外部網路請求。
  • 選完服務後「下一步」的位置：v1 在 y=985（視窗 844，畫面外），v2 在 y=780（畫面內）。量測值，不算斷言。
  • 各步驟與狀態在 390 與 1440 寬截圖。v1 逐張審看；v2 逐張看了受影響的畫面，其餘步驟原始碼與 v1 相同，沿用 v1 的審看結果。
  • 對比以 token 值計算：文字對底皆在 4.5:1 以上（最低 5.86:1），主按鈕深紫字配橘 7.12:1。只涵蓋計算過的色對。

沒有做的檢查

  • 真人試用，以及 v2 的重新試用。腳本中的回饋是示範，不是使用者測試證據。
  • 實機；390 寬是 Chromium 模擬的。Safari、Firefox 也沒測。
  • 螢幕閱讀器、200% 縮放。
  • 服務清單載入失敗與送出的其他錯誤，原型沒有涵蓋。另有已知限制：卡片與時段按鈕的邊框對底只有 1.32:1，未達 3:1，這兩者靠選取圓圈與文字辨識，不靠邊框；原型每次選取都重畫卡片，鍵盤方向鍵切換服務時焦點會跑掉。
  • 視覺方向技能沒有呼叫。技能只讀了候選技能的描述、沒讀完整指示，視覺語言由目標稿決定，紀錄把這點記為限制。

打開原型

單檔離線 HTML，原樣複製自試跑產物。並排頁與對照頁已把圖片路徑改成指向本站的檔案。表單只在頁面內驗證，送出是模擬，不會建立預約或寄出簡訊。
